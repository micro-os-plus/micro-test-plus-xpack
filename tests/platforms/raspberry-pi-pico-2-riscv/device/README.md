# device/rp2350

Definitions specific to the RP2350 device, for the Hazard3 (RISC-V) cores.

The result is a CMake interface library `micro-os-plus::device`.

## Implementation

This folder does not link any Pico SDK CMake library. The boot-ROM
metadata block, trap handler, and clock bring-up are entirely custom,
implemented directly on the RP2350 registers, the same way as the
sibling `raspberry-pi-pico-2-arm` platform (its RP2350/Cortex-M33
counterpart) and the other bare-metal platforms in this project.

The generic RISC-V reset entry (`gp`/`sp`/FPU bring-up, exporting
`reset_entry`) is **not** provided here any more: it now lives in
`micro-os-plus::architecture-riscv` itself (`src/reset-entry.S`), which
this platform links via `micro-os-plus::architecture` and which is
controlled by `MICRO_OS_PLUS_INCLUDE_ARCHITECTURES_RISCV_RESET_ENTRY_ENABLED`
in [include/micro-os-plus/architecture-defines.h](../include/micro-os-plus/architecture-defines.h)
(left at its default, enabled). Only the debugger entry point is still
platform-specific here; see "Custom implementation" below for why.

### Pico SDK headers used

`device/CMakeLists.txt` and `device/rp2350/CMakeLists.txt` add, as plain
include folders, header-only pieces of the
`@xpack-3rd-party/raspberrypi-pico-sdk` package:

- `.../common/boot_picobin_headers/include` — the picobin boot-ROM
  metadata format definitions (`boot/picobin.h`), used by
  [src/embedded-block-rp2350-riscv.c](src/embedded-block-rp2350-riscv.c)
- `.../rp2_common/pico_bootrom/include` and
  `.../rp2_common/boot_bootrom_headers/include` — `pico/bootrom_constants.h`
  (`BOOTROM_ENTRY_OFFSET`), used by
  [src/debugger-entry-point.S](src/debugger-entry-point.S) to re-enter the
  boot ROM; included with `NO_PICO_PLATFORM` defined (see
  `device/CMakeLists.txt`), so it does not pull in `pico/platform.h` ->
  `pico.h` -> `pico/config_autogen.h`, the same landmine described below
  for `hardware/hazard3.h`
- `.../rp2350/hardware_regs/include` — the plain register-offset/bit-field
  definitions (`hardware/regs/*.h`), used by
  [rp2350/src/system-clock.cpp](rp2350/src/system-clock.cpp) and by
  [../src/led-green.cpp](../src/led-green.cpp) (via
  [rp2350/include/micro-os-plus/rp2350/registers.h](rp2350/include/micro-os-plus/rp2350/registers.h))

Deliberately **not** used: the SDK's CMSIS `RP2350.h` (Arm/CMSIS-Core
specific, unusable from a RISC-V compiler; used instead by the sibling
`raspberry-pi-pico-2-arm` platform), the SDK's own
`hardware/structs/*.h`, and `hardware/hazard3.h` -- none of these are
usable standalone: all three eventually go through
`hardware/address_mapped.h` or a direct `#include "pico.h"`, which
requires `pico/config.h` -> `pico/config_autogen.h`, a header normally
generated by the SDK's own CMake build (`pico_generate_config_header`),
which this platform does not run; `hardware/hazard3.h` is also simply
unneeded here, since this platform implements no Hazard3-specific IRQ
dispatch (see "Custom implementation" below). See
[rp2350/include/micro-os-plus/rp2350/registers.h](rp2350/include/micro-os-plus/rp2350/registers.h)
for the resulting `RP2350_REG32()` accessor used throughout instead.

No Pico SDK CMake targets are linked, and no other Pico SDK sources are
compiled.

### Custom implementation

- [src/debugger-entry-point.S](src/debugger-entry-point.S) — the one
  piece of startup code still written here rather than reused from
  `micro-os-plus::architecture-riscv`: RP2350 needs `_debugger_entry_point`
  (the ELF's `ENTRY()`, where GDB's `load` command leaves PC once flashing
  finishes) to re-enter the boot ROM at `BOOTROM_ENTRY_OFFSET` before
  falling through to `reset_entry`, so that hardware bring-up the boot
  ROM would normally do on a real reset still happens when the
  application is started by a debugger rather than a cold reset.
  `architecture-riscv` ships its own generic (no-op) version of this
  file, disabled here via
  `MICRO_OS_PLUS_INCLUDE_ARCHITECTURES_RISCV_DEBUGGER_ENTRY_POINT_ENABLED`
  in
  [include/micro-os-plus/architecture-defines.h](../include/micro-os-plus/architecture-defines.h)
  so this platform-specific one is used instead ("reimplement this
  function in the project", per that file's own comment).
- [src/trap-handler.cpp](src/trap-handler.cpp) — installs a minimal
  Direct-mode `mtvec` handler that spins on any unexpected trap. No test
  running on this platform arms a real interrupt source (the LED is
  polled GPIO, the clocks are one-shot register pokes at startup, and
  semihosting goes through the debug probe), so this deliberately does
  not implement Hazard3's vectored `mtvec` mode or its
  `meiea`/`meipa`/`meifa`/`meinext` external-interrupt-array dispatch
  (the mechanism the Pico SDK's own `crt0_riscv.S` uses) — built entirely
  on `micro-os-plus::architecture-riscv`'s existing CSR/instruction
  wrappers (`riscv::csr::mtvec()`, `riscv::csr::mcause()`,
  `riscv::architecture::wfi()`), with no hand-written trap-entry assembly
  of its own.
- [src/embedded-block-rp2350-riscv.c](src/embedded-block-rp2350-riscv.c) —
  the picobin `IMAGE_DEF` metadata block, carrying an `ENTRY_POINT` item
  with `reset_entry`'s address and the initial stack pointer, for the
  boot ROM to use on a cold reset; see "Known limitation" below.
- [rp2350/src/system-clock.cpp](rp2350/src/system-clock.cpp) — brings up
  the crystal oscillator and the system PLL to a calibrated 150 MHz
  clk_sys; algorithmically identical to the ARM platform's version, only
  ported from CMSIS struct access to `RP2350_REG32()`.

### Known limitation: boot-ROM cold-reset entry not yet confirmed on hardware

Two distinct ways this platform can start have been exercised, with
different confidence levels:

- **Debugger-launched** (GDB `load` + `continue`, no explicit chip
  reset): confirmed working on real hardware via OpenOCD/GDB. `load`
  leaves PC at `_debugger_entry_point`, which re-enters the boot ROM at
  `BOOTROM_ENTRY_OFFSET` and falls through to `reset_entry` and `main`.
- **Cold reset** (the boot ROM scanning flash for the picobin
  `IMAGE_DEF`/`ENTRY_POINT` block on its own, e.g. via OpenOCD's
  `program ... verify` + `reset` flow, or an actual power cycle): still
  **not** confirmed. A `monitor reset init` issued after `reset_entry`/
  `_debugger_entry_point` breakpoints were set was observed to still
  reach `main`, but without stopping at either breakpoint first --
  consistent with either the boot ROM not entering the image the way the
  `ENTRY_POINT` item intends, or the reset invalidating those
  already-set breakpoints without GDB noticing (both remain open;
  distinguishing them needs a fresh session that only sets breakpoints
  *after* the reset it will run from). Unlike Arm, RISC-V has no
  implicit "vector table at image start" boot convention, so this path
  depends entirely on the boot ROM correctly parsing the `ENTRY_POINT`
  item -- matching the Pico SDK's own `pico_crt0/embedded_start_block.inc.S`
  layout for `__riscv` builds, but not yet independently verified here.
  This is a known, deliberately deferred follow-up.
