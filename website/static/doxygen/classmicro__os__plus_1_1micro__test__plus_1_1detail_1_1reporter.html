Detailed Description

The reporter class is responsible for presenting test results within the µTest++ framework. It accumulates output in a buffer, using basic output operators for strings, characters, booleans, numbers, and pointers, and writes it to the console and to an optional output file.

For failed checks, the reporter prints the actual values of the operands, pre-formatted by its expression_formatter (with type suffixes for numbers). The class supports multiple verbosity levels and colour-coded output to distinguish between passed and failed checks.

The pure virtual member functions report the beginning and end of the session, the suites, and the test cases, and format the pass and fail results; they are implemented by reporter_human and reporter_tap. The concrete reporter is created by the runner, as selected by the --reporter command-line option, or by runner_options::selected_reporter.

The reporters are internal to the framework: their public members are the protocol between the runner, the test nodes, the checks, and the reporter, and custom reporters are not supported. The applications select a reporter with the --reporter command-line option, or with the runner_options, and read the verbosity with runner::verbosity_level().

bool is_requirement )
pure virtual

Called by runner::abort() between begin_session() and end_session(), before the abort handler and ::abort(); neither the end_test_case() of the running test cases, if any, nor end_session() are called afterwards. The abort is caused either by a failed require(), when exceptions are disabled, after the failure was added to the output buffer, or by an explicit call of runner::abort(), from a test case body, from a suite body, or from the application.

Implementations display the buffered results, if any, with the context that identifies the running test case, followed by a line with the location of the abort, unless the verbosity is silent, and write them to the output file, if open, since the totals are never reached. They then clear the buffer, since the abort handler may throw an exception that the application catches, and the results must not be written again.
