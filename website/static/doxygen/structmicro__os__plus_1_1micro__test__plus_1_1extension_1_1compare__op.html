Detailed Description

template<class Lhs_T, class Rhs_T, class Compare_T>
struct micro_os_plus::micro_test_plus::extension::compare_op< Lhs_T, Rhs_T, Compare_T >

Derived from binary_op, this struct compares the left-hand operand with the right-hand operand, using the operator defined by the tag Compare_T (equal_to, not_equal_to, greater, greater_equal, less, or less_equal). It is used within test expressions to provide human-readable relational assertions, with the actual and expected values, and the symbol of the tag, reported upon failure.

The tag is passed as an empty constructor argument, so that all three template arguments are deduced, for example compare_op{ lhs, rhs, equal_to{} }. A factory function would do the same, but at -O0 it adds one function per instantiation.

It is also public, as extension::compare_op, so that the applications can define their own comparisons with their own tags. A tag is an empty struct with:

  • a static constexpr const char* symbol, written between the operands in the failure reports, with the surrounding spaces (for example " divides ");
  • a static apply (lhs, rhs) member function template, which receives the unwrapped operands (the values of the to_* wrappers and of the literals) and returns the result as bool;
  • optionally, a static constexpr bool within_tolerance_result; when present, and an operand is a floating-point wrapper (see extension::has_epsilon), the operands within the tolerance give this result, as for the built-in comparators; when absent, the tolerance is ignored.

The operands are not copied: the temporaries are moved into the comparator, and the named operands of class type are referred to (see stored_operand_t). A comparator built in a function from its const& parameters refers to the arguments of that function, so it must be checked in the statement that calls the function.

Evaluates the comparison inside an immediately invoked lambda, which converts the result of Compare_T::apply() to bool, and passes it to the binary_op base class constructor:

  • for the framework constants with static value members (the numeric literals), the two values are compared directly;
  • if at least one operand is a framework floating-point wrapper with an epsilon member, and the tag defines a within_tolerance_result (all the built-in tags do), operands within the tolerance give this result; otherwise the unwrapped values are compared; the tags of the application without it ignore the tolerance;
  • for all other types, the framework wrappers are unwrapped, and the values, including the types of the application, are compared as they are.
