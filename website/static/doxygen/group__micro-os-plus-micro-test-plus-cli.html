Options for controlling the test output at run time.

The µTest++ framework offers flexible control over test-output verbosity, allowing users to tailor the level of detail to their specific requirements and workflow.

By default, the reporter presents detailed results only for failed test cases, while successful test cases are summarised in a single line, indicating the total number of passed and failed checks.

Example
$ minimal-test one two --reporter=tap
TAP version 14
# Subtest: Minimal
# Subtest: Check various conditions
1..0
ok 1 - Check various conditions # { passed, 2 checks }
1..1
ok 1 - Minimal # { passed, 2 checks in 1 test case, time: X.XXX ms }
1..1
# { total: 2 checks passed, 0 failed, in 1 test case, 1 test suite, time: X.XXX ms }

Reporter

By default, the µTest++ output follows the TAP rules.

The human-readable format of the initial releases is also available. It is intended for the people who read the console output, while the TAP format is intended for the integration with other tools.

If needed, more reporting formats (like JUnit, JSON, etc.) can be added.

To explicitly ask for a specific format:

  • --reporter=tap – the default TAP reporter
  • --reporter=human – the human-readable reporter

Colours

The human reporter highlights the results in colour. By default, the colours are used only when stdout is a terminal, which can be detected only on POSIX platforms. To select them explicitly, as in the GNU tools:

  • --color=auto – use colours only when the output is a terminal (the default)
  • --color=always, or --color alone – always use colours, for example in the CI systems that render the ANSI escape sequences but do not provide a terminal
  • --color=never – never use colours

As in the GNU tools, the value must be attached with =, and the synonyms yes and force (for always), no and none (for never), and tty and if-tty (for auto) are also accepted. For compatibility with Catch2 and Boost UT, --use-colour=<mode> or --use-colour <mode>, with yes, no, or auto (or any other value of --color), is also accepted. The TAP reporter never uses colours, and the output file never receives them.

On platforms without a command line, the mode can be set in runner_options::colour.

Verbosity

By default, µTest++ displays a summary line for each passing test case and full expectation details for each failing one.

To adjust the verbosity, the following command-line options are available:

  • --verbose – display all expectations, regardless of outcome
  • --quiet – display only the session totals and, with the TAP reporter, one result line per test suite; the failed checks are not displayed
  • --silent – suppress all console output and return only the exit code

On platforms without a command line, the level can be set in runner_options::verbosity_level.

The source code for these examples is in tests/sources/minimal/src/main.cpp.

Verbose mode

In verbose mode, the µTest++ reporter provides detailed output for every expectation, irrespective of whether it passes or fails.

Example
$ minimal-test one two --verbose --reporter=tap
TAP version 14
# Subtest: Minimal
# Subtest: Check various conditions
ok 1 - answer is 42
ok 2 - condition is true
1..2
ok 1 - Check various conditions # { passed, 2 checks }
1..1
ok 1 - Minimal # { passed, 2 checks in 1 test case, time: X.XXX ms }
1..1
# { total: 2 checks passed, 0 failed, in 1 test case, 1 test suite, time: X.XXX ms }

Quiet mode

In quiet mode, the µTest++ reporter displays only the overall session totals. The TAP reporter also displays one ok/not ok line per test suite, with the plan counting them, so that the output remains a valid TAP document, which the TAP consumers read as failed when a suite failed.

Example
$ minimal-test one two --quiet --reporter=tap
TAP version 14
ok 1 - Minimal # { passed, 2 checks in 1 test case, time: X.XXX ms }
1..1
# { total: 2 checks passed, 0 failed, in 1 test case, 1 test suite, time: X.XXX ms }

Quiet mode tells whether the run failed, not what failed: the failed checks, their locations, and their test cases are not displayed. This is by design, since displaying in full only the failed test cases is what the default mode does. To learn what failed, run without --quiet, or keep --quiet and add --output-file with the TAP reporter, whose file always receives the complete report, whatever the verbosity:

$ sample-test --quiet --output-file=sample-test.tap

With the human reporter, the output file is complete only in the default and verbose modes, so in quiet mode neither the console nor the file shows the failures.

When exceptions are not enabled and a failed requirement aborts the test execution, the results of the aborted test case are displayed in quiet mode as well, since the totals are never reached.

Silent mode

In silent mode, the µTest++ reporter suppresses all console output, and the framework returns only the exit code; the output file, if any, is still written.

Output File

  • --output-file=<path> or --output-file <path> – write a copy of the report to a file

The file never receives colours. With the TAP reporter, it always receives the complete report, whatever the verbosity, so it can be passed to other tools; with the human reporter, it is complete only in the default and verbose modes. If the file cannot be opened, the error is reported on stderr, the report is written only to the console, and the exit code is 2. On platforms without a command line, the path can be set in runner_options::output_file_path.

Filter

By default, all test suites and test cases are run. To run only some of them, the --filter option selects them by name, as --grep does in node-tap:

  • --filter=<pattern> or --filter <pattern> – run only the suites and the test cases whose names match the patterns

The option may be repeated, one pattern per nesting level: the first pattern applies to the suite names, the second to the names of the test cases, and each further pattern to the names of the test cases nested one level deeper. The levels without a pattern are not filtered; to filter only the test cases, use * for the suites.

In a pattern, * matches any sequence of characters, including an empty one, ? matches any single character, and | separates alternatives. The match is case-sensitive, and the pattern must cover the whole name; for example, Args does not select a suite named Args suite, but Args* and Args*|*namespace* do. Since the patterns usually contain wildcards, they must be quoted, to prevent the shell from expanding them.

The suites and the test cases that are not selected are reported as skipped, keep their numbers in the TAP plans, and their code is not run. The top suite is never skipped as a whole, since its body is main(), but its test cases are filtered like those of any other suite.

On platforms without a command line, the patterns can be set in runner_options::filter_patterns.

Example
$ sample-test one two --filter='*namespace*'
TAP version 14
# Subtest: Sample
...
ok 1 - Sample # { passed, 31 checks in 13 test cases, time: X.XXX ms }
ok 2 - Args suite # SKIP filtered
# Subtest: Explicit namespace suite
...
ok 3 - Explicit namespace suite # { passed, 2 checks in 2 test cases, time: X.XXX ms }
# Subtest: Implicit namespace suite
...
ok 4 - Implicit namespace suite # { passed, 2 checks in 2 test cases, time: X.XXX ms }
1..4
# { total: 35 checks passed, 0 failed, in 17 test cases, 4 test suites, 1 skipped, time: X.XXX ms }

To run only the test cases named Check one of the same suites:

$ sample-test one two --filter='*namespace*' --filter='Check one'
...
# Subtest: Explicit namespace suite
# Subtest: Check one
1..0
ok 1 - Check one # { passed, 1 check }
ok 2 - Check two # SKIP filtered
1..2
ok 3 - Explicit namespace suite # { passed, 1 check in 1 test case, 1 skipped, time: X.XXX ms }
...
1..4
# { total: 2 checks passed, 0 failed, in 2 test cases, 15 skipped, 4 test suites, 1 skipped, time: X.XXX ms }

The test cases of the top suite Sample are skipped too, since its name does not match the first pattern.

Listing the Test Cases

  • --list-tests, or --list – list the test cases instead of running them, as in Catch2 and Boost UT

The suite bodies run, to create their test cases, but the test case bodies do not, so no check is evaluated. The selected test cases (see the filter above) are listed under the names of their suites; the nested test cases are not listed, since they are created by the bodies of their parents. The list is written to the console, unless the verbosity is silent, and to the output file, if any, and the exit code is 0 (or 2 after an option error).

$ sample-test --list-tests
All available test cases:
Sample
Check various conditions
...
...

The header is Matching test cases: when there are filter patterns. On platforms without a command line, the listing can be requested with runner_options::list_tests, and checked with runner::is_listing().
