## Rationale

At its most basic level, the simplest testing approach requires no framework at all.
A test for a C or C++ project can readily be written without any framework,
perhaps utilising the standard `assert()` macro or a similar user-defined mechanism.

However, with this mechanism, failed assertions typically abort the test, and when dealing with multiple
test cases containing numerous checks, it is **preferable to obtain a comprehensive report**.

Testing frameworks address this need by providing convenient mechanisms for writing
various checks and generating clear, structured reports.

The xPack Framework already includes ready-to-use
support for several testing frameworks
([Google Test](https://github.com/xpack-3rd-party/googletest-xpack),
[Catch2](https://github.com/xpack-3rd-party/catch2-xpack),
[Boost UT](https://github.com/xpack-3rd-party/boost-ut-xpack)).
Nevertheless, these frameworks tend to be quite demanding in terms of memory resources, and
the learning curve required to master them can be rather steep.

Therefore, for embedded projects, a **simpler solution** with a **smaller
memory footprint** was considered a valuable addition.

## Overview

The initial version of the **µTest++ Testing Framework** drew its primary inspiration from
[Node TAP](https://node-tap.org), with a strong emphasis on simplicity. Version 3.x was heavily influenced by [Boost UT](https://boost-ext.github.io/ut/), from which it derived its function comparators,
while version 4.x represented a complete redesign, drawing even more inspiration from
[Node TAP](https://node-tap.org) by passing explicit references to parent objects into test and suite callbacks.

## Concepts and features

- For more complex applications, test cases may be organised into test suites.
- Test suites can reside in separate compilation units and automatically register themselves with the test runner.
- A **test suite** is a named collection of test cases.
- A **test case** comprises a sequence of **test conditions** (also referred to as **tests** or **checks**), which are expectations or requirements — conditions anticipated to be true.
- Tests are based on logical expressions, typically evaluating a result and comparing it to an expected value.
- For C++ projects, it is also possible to verify whether evaluating an expression results in an **exception** being thrown.
- Each test either passes or fails.
- For **expectations**, the runner maintains a count of occurrences.
- **Requirements** are critical conditions that must be satisfied for the test case to proceed.
- A failed requirement stops the current test case; the run continues with the next one.
- Test progress is displayed on STDOUT, with each test on a separate line, prefixed by an indication of whether the test passed or failed.
- Failed tests indicate the location within the file and, where possible, the actual values used in the evaluation.
- The primary result of the test is returned to the system as the process exit code.
- Optionally, the detailed test results can be written to a separate file, for example in TAP format.

A test suite is deemed successful if there are no failed tests.

If all test suites are successful, the process returns an exit value of 0.

## Getting started

### Minimal test

The most basic test comprises a single test case with a single expectation; for example:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

// For convenience, alias the fully qualified namespace to a shorter name.
namespace mt = micro_os_plus::micro_test_plus;

int
main(int argc, char* argv[])
{
  // Create a local instance of the runner. Name the top suite.
  mt::runner tr;

  // Initialise the runner and get a reference to the top suite.
  auto& ts = tr.initialise(argc, argv, "Minimal");

  // Perform a simple test, with a single expectation.
  ts.test ("Check truth", [] (auto& t) {
    t.expect (true);
  });

  return tr.run ();
}
```

:::info C++ Lambdas
The second argument passed to the `test()` function is a **C++ lambda**, which is an unnamed inline function.

µTest++ recommends using lambdas whenever possible, but also supports passing any C++ callable object, such as pointers to functions, functors, `std::function`, etc.
:::

### TAP output

By default, when a test is executed, the output conforms to the **TAP14 (Test Anything Protocol version 14)** [specification](https://testanything.org/tap-version-14-specification.html), a well-established protocol for communication between tested logic and test harnesses.

For the above test, the verbose output would look like:

```console
TAP version 14
# Subtest: Minimal
    # Subtest: Check truth
        ok 1 - true
        1..1
    ok 1 - Check truth # { test case passed, 1 check }
    1..1
ok 1 - Minimal # { test suite passed, 1 check in 1 test case, time: 0.007 ms }
1..1
# { total: 1 check passed, 0 failed, in 1 test case, 1 test suite, time: 0.030 ms }
```

In the `ok`/`not ok` lines, the names of the suites and test cases, the messages, and the expressions are escaped as the specification recommends: each `#` is written as `\#`, and each `\` as `\\`, so that a `#` in a name (for example `parser # TODO rework`) is not read as a `TODO` or `SKIP` directive, which would hide a failure; the TAP consumers remove the escapes. The line breaks are replaced by spaces, so that a name or a message always fits on its line. The `# Subtest:` lines, which are comments, show the names as they are, with only the line breaks replaced.

### Testing a computed value

A slightly more practical example would verify the result of a computed value; for instance:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

static int
compute_answer()
{
  return 42;
}

int
main(int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise(argc, argv, "The Answer");

  ts.test ("Check answer", [] (auto& t) {
    t.expect (compute_answer() == 42) << "answer is 42";
  });

  return tr.run ();
}
```

```console
TAP version 14

# Subtest: The Answer
    # Subtest: Check answer
        ok 1 - answer is 42
        1..1
    ok 1 - Check answer # { test case passed, 1 check }
    1..1
ok 1 - The Answer # { test suite passed, 1 check in 1 test case, time: 0.007 ms }
1..1
# { total: 1 check passed, 0 failed, in 1 test case, 1 test suite, time: 0.030 ms }
```

If the function returns an incorrect value, the test will fail; for example:

```cpp
static int
compute_answer()
{
  return 42 + 1;
}
```

In this case, the test output will be as follows:

```console
TAP version 14

# Subtest: The Answer

    # Subtest: Check answer
        not ok 1 - answer is 42
            ---
            at:
              filename: main.cpp
              line: 17
            ...
        1..1
    not ok 1 - Check answer # { test case FAILED, 0 checks passed, 1 failed }
    1..1
not ok 1 - The Answer # { test suite FAILED, 0 checks passed, 1 failed, in 1 test case, time: 0.039 ms }
1..1
# { total: 1 check passed, 1 failed, in 1 test case, 1 test suite, time: 0.077 ms }
```

The output identifies the failed test at line 17, but does not provide further details, such as the actual incorrect value.

### More advanced comparators

To obtain a more informative report, such as the actual incorrect value, the test should be slightly more detailed and employ custom comparators or operators; for example:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

static int
compute_answer()
{
  return 42+1;
}

int
main(int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise(argc, argv, "The Answer");

  ts.test ("Check answer with comparator", [] (auto& t) {
    t.expect (mt::eq (compute_answer (), 42)) << "answer is 42";
  });

  ts.test ("Check answer with operator", [] (auto& t) {
    using namespace mt::operators;
    using namespace mt::literals;

    t.expect (compute_answer () == 42_i) << "answer is 42";
    t.expect (mt::to_i {compute_answer ()} == 42) << "answer is 42";
  });

  return tr.run ();
}
```

The output would be:

```console
TAP version 14

# Subtest: The Answer

    # Subtest: Check answer with comparator
        not ok 1 - answer is 42
            ---
            expect: 43 == 42
            at:
              filename: main.cpp
              line: 69
            ...
        1..1
    not ok 1 - Check answer with comparator # { test case FAILED, 0 checks passed, 1 failed }

    # Subtest: Check answer with operator
        not ok 1 - answer is 42
            ---
            expect: 43 == 42
            at:
              filename: main.cpp
              line: 76
            ...
        not ok 2 - answer is 42
            ---
            expect: 43 == 42
            at:
              filename: main.cpp
              line: 77
            ...
        1..2
    not ok 2 - Check answer with operator # { test case FAILED, 0 checks passed, 2 failed }
    1..2
not ok 1 - The Answer # { test suite FAILED, 0 checks passed, 3 failed, in 2 test cases, time: 0.036 ms }
1..1
# { total: 0 checks passed, 3 failed, in 2 test cases, 1 test suite, time: 0.067 ms }
```

In the first case, `eq()` is a **function comparator**, a function not only capable of comparing almost any type but also of recording the values of its operands. Similar functions exist for all types of comparisons.

In the second case, a **custom operator** is used. To avoid conflicts with other operators, this custom operator is defined in a separate namespace (which must be explicitly referenced as shown) and matches only operands of specific types.

To cast the integer constant `42` to such a specific type, a **custom literal** (`_i`) is available, also defined in the separate `micro_test_plus` namespace.

In addition to literals for constants, there are also **definitions to cast expressions**.

For the custom operators to match, at least one operand must be of the specific type, usually the constant via a literal. If both are expressions, at least one must be cast.

### More complex tests

For simple scenarios, invoking multiple test cases in `main()` may suffice.

For more complex applications, test cases can be grouped into test suites and invoked, potentially multiple times with different arguments (see the [Test suites](#test-suites) section).

## C++ API

### Namespaces

The definitions are organised within several namespaces under `micro_os_plus`:

- `micro_os_plus::micro_test_plus` (commonly aliased as `mt`)
- `micro_os_plus::micro_test_plus::operators`
- `micro_os_plus::micro_test_plus::literals`
- `micro_os_plus::micro_test_plus::utility`

`micro_os_plus` is the primary µOS++ namespace, and `micro_test_plus` is the
namespace for µTest++.

The `operators` namespace provides custom operators, while the `literals`
namespace defines user-defined literals (such as `1_i`).

### Test runner

The test framework is implemented as a runner object, which must be instantiated and initialised.

#### Instantiation

The runner object must be instantiated by the application:

```cpp
mt::runner tr;
```

For simple tests, the runner can be a local stack-allocated object in `main()`.

#### Initialisation

After instantiation, the runner **must** be initialised, usually by passing the main arguments and the name of the top default suite:

```cpp
auto& ts = tr.initialise(argc, argv, "Main");
```

The initialisation method returns the default top suite, which is required later to create test cases.

On platforms without a command line, such as embedded applications without semihosting arguments, the runner can be initialised with the options set directly, starting from the defaults, instead of the main arguments:

```cpp
mt::runner_options options{};
options.selected_reporter = mt::reporter_kind::human;
options.verbosity_level = mt::verbosity::verbose;

auto& ts = tr.initialise(options, "Main");
```

The members of `runner_options` correspond to the command-line options: `selected_reporter` to `--reporter`, `verbosity_level` to `--silent`, `--quiet`, and `--verbose`, `output_file_path` to `--output-file`, and `filter_patterns` to `--filter`.

#### Test result

To run the registered suites, end the session, and return the test result as the process exit code, the runner provides the `run()` method; the session runs only once, and later calls return the same result:

```cpp
return tr.run ();
```

The result is 0 if all checks passed, and 1 otherwise, including when a suite was added too late (see [Non-static test suites](#non-static-test-suites)). If the command-line options, or the `runner_options`, were not valid (an unknown reporter name, a missing option argument, or an output file that cannot be opened), the error is reported on `stderr` when the runner is initialised, the option is ignored, and the tests are still run, but the result is 2.

#### Aborting the test execution

When exceptions are not enabled, a failed requirement cannot stop only its test case (see [Requirements](#requirements)), so it aborts the whole test execution: the remaining test cases and suites do not run, `run()` does not return, and no totals are written. Before the process is terminated:

1. the reporter displays the results of the current test case, ending with the failed requirement, which is marked as `test execution aborted` (the TAP reporter adds no marker, since its `Bail out!` line, below, reports the abort); they are preceded by the name of the test case, and by those of the outer test cases, unless already displayed, so that the failure cannot be attributed to the previous test case;
2. the TAP reporter adds a `Bail out! Requirement failed at <file>:<line>` line, which tells the TAP consumers that the run stopped early, not that the output was truncated;
3. `runner::abort()` writes `error: test execution aborted at <file>:<line>` to `stderr`, flushes the standard streams, calls the abort handler, if one was set (see below), and then `::abort()`.

With `--quiet`, which otherwise displays only the totals, the results of the aborted test case are displayed as well, since the totals are never reached; the passed checks are included, as the context of the failure. With `--silent`, nothing is displayed, but the `stderr` line is still written. If an output file is used, the results are written to it too (with the human reporter, only with normal or verbose verbosity, as for the other test cases).

For example, with the human reporter, the end of the output is:

```
    ✓ Check various conditions - passed (2 checks)

    • Parse configuration
        ✓ file found
        ✗ sections parsed FAILED (main.cpp:42, 0 > 0) - test execution aborted

error: test execution aborted at main.cpp:42
```

and with the TAP reporter:

```
    # Subtest: Parse configuration
        ok 1 - file found
        not ok 2 - sections parsed
          ---
          condition: "0 > 0"
          at:
            filename: main.cpp
            line: 42
          ...
Bail out! Requirement failed at main.cpp:42

error: test execution aborted at main.cpp:42
```

Unless the abort handler ends the program otherwise, the process ends with `SIGABRT`, so a test harness sees a terminated process, not an exit code returned by `run()`.

On embedded targets, where terminating the process is not meaningful, the application can set a handler, called before `::abort()`, for example to reset the target or to signal the result to the debugger:

```cpp
tr.set_abort_handler ([] (const mt::reflection::source_location& sl)
  {
    // Signal the failure, then reset the target; do not return.
  });
```

If the handler returns, `::abort()` is still called.

Refer to the [Test Runners](/docs/api/groups/micro-os-plus-micro-test-plus-runners/) reference page.

### Test cases

Test cases are collections of checks to be executed within the same environment.

Test case objects can be created using the `test()` method provided by the test suite object:

```cpp
template <typename Callable_T, typename... Args_T>
void test (const detail::test_name& name, Callable_T&& func, Args_T&&... arguments);
```

The name is a string literal or a `const char*`, converted implicitly to
`detail::test_name`, which also records the location of the `test()`
call.

The additional arguments, if any, are passed to the callable after the
test case reference. They are copied when `test()` is called, as they
are by `runner::suite()` and by the `static_suite` constructor, whose
suites run later, so a reference parameter refers to the copy. To
refer to the caller's object, pass a pointer, or `std::ref (object)`
for a parameter of type `T&`. A lambda can also capture the values
instead.

When exceptions are enabled, an exception that escapes the body of a
test case is reported as a failed check of that test case, at the
location of the `test()` call, and the run continues with the next test
case; the message includes the result of `what()` for a
`std::exception`:

```console
    • Parse configuration
        ✓ header is valid
        ✗ unexpected exception: invalid key FAILED (config.cpp:42)
    ✗ Parse configuration - FAILED (1 check passed, 1 failed)
```

Similarly, an exception that escapes the body of a test suite, outside
its test cases (for example from a set-up step), is reported as a
failed check of that suite, after the test cases already run; the
rest of the suite body is skipped, and the run continues with the next
suite. Since the suites do not record a source location, none is
shown:

```console
• Configuration suite

    ✓ Parse configuration - passed (1 check)

    ✗ unexpected exception in the suite body: no such file FAILED
✗ Configuration suite - FAILED (1 check passed, 1 failed, in 1 test case)
```

For the exception to reach the framework, the body, of a test case or
of a test suite, must not be declared `noexcept`; otherwise the
exception calls `std::terminate()`, and ends the program.

Refer to the [Test Cases](/docs/api/groups/micro-os-plus-micro-test-plus-test-case/) reference page.

### Expectations and requirements

Expectations and requirements are checks that evaluate expressions
yielding boolean values; they differ in what happens after a failure.

Both are created with methods of the test case objects, and return an
object to which a message can be appended with `<<`; the check is
reported at the end of the statement:

```cpp
template <class Expr_T>
  requires type_traits::checkable<Expr_T>
auto expect (const Expr_T& expr);

template <class Expr_T>
  requires type_traits::checkable<Expr_T>
auto require (const Expr_T& expr);
```

A failed **expectation** is reported and counted, and the test case
continues, so that all its checks are evaluated and reported in one run.

#### Requirements

A failed **requirement** is reported and counted as a failed
expectation, and then the rest of the test case is skipped, since the
following checks would be meaningless; the run continues with the next
test case:

```cpp
ts.test ("Parse configuration", [] (auto& t)
  {
    auto config = parse ("config.json");
    t.require (config.has_value ()) << "configuration parsed";

    // Not reached if the configuration could not be parsed.
    t.expect (config->version == 2) << "version 2";
  });
```

A failed requirement in a nested test case stops only the nested test
case; the outer test case continues, and fails because of it.

The test case is stopped by throwing an exception, at the end of the
statement, after the message was appended. It is not derived from
`std::exception`, so a `catch (const std::exception&)` in the test case
body does not intercept it; a `catch (...)` does, and must rethrow it
with `throw;`. The test case body must not be `noexcept`, since the
exception would call `std::terminate()`.

The human reporter marks the failed requirement with
`- test case stopped`, after the location; the TAP reporter reports it
like any other failed check, as node-tap does, and the stop is shown by
the plan of the test case, which follows it:

```
    • Parse configuration
        ✗ configuration parsed FAILED (main.cpp:4) - test case stopped
```

Without exceptions (for example with `-fno-exceptions`, common on
embedded targets), the test case cannot be stopped, and a failed
requirement aborts the whole test execution, as described in
[Aborting the test execution](#aborting-the-test-execution): the
results of the test case are displayed, ending with the failed
requirement, but the remaining test cases do not run and no totals are
written.

`assume()` is a deprecated alias of `require()`. The name was
misleading: in JUnit and Hypothesis, an unmet assumption **skips** the
test, which is not counted as failed, while in µTest++ it fails it.

#### Comparison with other frameworks

The plain `assert()` macro, mentioned in the [Rationale](#rationale),
terminates the whole program at the first failure. Test frameworks
distinguish the non-fatal checks, which only report the failure, from
the fatal ones, which also stop the test; most of them stop only the
current test case, which is also the behaviour of `require()`:

| Framework | Non-fatal | Fatal | After a fatal failure |
| --- | --- | --- | --- |
| µTest++ | `expect()` | `require()` | the test case is stopped |
| GoogleTest | `EXPECT_*()` | `ASSERT_*()` | the current function returns |
| Catch2 | `CHECK()` | `REQUIRE()` | the test case is stopped |
| doctest | `CHECK()` | `REQUIRE()` | the test case is stopped |
| Boost.Test | `BOOST_CHECK()` | `BOOST_REQUIRE()` | the test case is stopped |
| Boost.UT | `expect()` | `expect (...) << fatal` | the program exits |
| Unity (C) | — | `TEST_ASSERT_*()` | the test is stopped |
| JUnit | — | `assert*()` | the test is stopped |
| C library | — | `assert()` | the program is aborted |

Some differences are worth noting:

- in GoogleTest, `ASSERT_*()` returns only from the function in which
  it is used; if this is a helper function, the test continues after
  the call;
- Catch2, doctest, and Boost.Test also stop the test case with an
  exception; without exceptions, Catch2 calls `std::terminate()`,
  and doctest either removes `REQUIRE()`, or makes it behave as
  `CHECK()`;
- Boost.UT reports the fatal failure and calls `std::exit()`, so the
  remaining tests do not run, as with the previous versions of
  `assume()`;
- Unity, a C framework, stops the test with `longjmp()`, which does not
  run the destructors of the C++ objects;
- in JUnit, an unmet `assume*()` aborts the test, which is reported as
  skipped, not as failed.

Refer to the [Expectations](/docs/api/groups/micro-os-plus-micro-test-plus-expectations/)
and [Requirements](/docs/api/groups/micro-os-plus-micro-test-plus-requirements/) reference pages.

### Nested test cases

Test cases can be defined in a nested manner, i.e., a test case can include not only checks, but also other test cases, at any nesting level.

A nested test case is created by calling `test()` on the outer test
case, and runs immediately; a failed nested test case also fails the
outer one:

```cpp
ts.test ("Parse configuration", [] (auto& t)
  {
    t.expect (parse ("config.json")) << "configuration parsed";

    t.test ("Defaults", [] (auto& nt)
      {
        nt.expect (default_port () == 80) << "default port";
      });
  });
```

A test case started on the suite, with `ts.test()`, from the body of a
running test case (for example via a captured suite reference), cannot
follow it in the report, since the running test case has not ended; it
runs nested in the innermost running test case, as if `t.test()` had
been called.

### Function comparators

To facilitate clear reporting of differences between expected and
actual values in failed conditions, several **generic comparator functions**
are provided.

```cpp
template <class Lhs_T, class Rhs_T>
auto eq(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto ne(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto lt(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto le(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto gt(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto ge(const Lhs_T& lhs, const Rhs_T& rhs);
```

The C strings (`char` arrays, including the string literals, and `char`
pointers) are compared by content, also with `std::string` and
`std::string_view`, so `mt::eq (actual, "abc")` checks the characters,
not the addresses; a null `char` pointer is equal only to another null
pointer (or `nullptr`), not to an empty string. The other pointers and
arrays (including `uint8_t` buffers) are compared by address.

Refer to the [Function Comparators](/docs/api/groups/micro-os-plus-micro-test-plus-function-comparators/) reference page.

### Logical functions

Complex expressions may be evaluated in a single statement using the logical
functions `both()`, `either()`, and `negate()`, the function forms of the
`&&`, `||`, and `!` operators; `either()` is an inclusive or, true also
when both operands are true.

```cpp
template <class Lhs_T, class Rhs_T>
auto both (const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto either (const Lhs_T& lhs, const Rhs_T& rhs);

template <class Expr_T>
auto negate (const Expr_T& expr);
```

Refer to the [Logical Functions](/docs/api/groups/micro-os-plus-micro-test-plus-logical-functions/) reference page.

### Checking exceptions

It is also possible to check various **exception-related conditions**.

```cpp
// Check for any exception.
template <class Callable_T>
auto throws (const Callable_T& expr);

// Check for a specific exception.
template <class Exception_T, class Callable_T>
auto throws (const Callable_T& expr);

// Check for no exception at all.
template <class Callable_T>
auto nothrow (const Callable_T& expr);
```

### Operators

For convenience, it is also possible to overload the
`==`, `!=`, `<`, `>`, `<=`, and `>=` operators:

```cpp
namespace operators {
  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator== (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator!= (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator< (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator<= (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator> (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator>= (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator and (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class Lhs_T, class Rhs_T>
    requires type_traits::any_op<Lhs_T, Rhs_T>
  auto operator or (const Lhs_T& lhs, const Rhs_T& rhs);

  template <class T>
    requires type_traits::is_op<T>
  auto operator not (const T& t);
}
```

Refer to the [Operators](/docs/api/groups/micro-os-plus-micro-test-plus-operators/) reference page.

### Strings

There are no operators for strings: the standard `==` and `!=`
operators would be selected for `std::string` objects, and they return
a plain `bool`, so a failed check could not show the strings; operators
for `std::string_view` objects would also replace the standard ones in
the application code that follows the `using namespace` directive. Use
`eq()` and `ne()`, which compare the strings by content, and show them
when the check fails:

```cpp
t.expect (mt::eq (actual, "fortytwo"sv))
    << "actual eq 'fortytwo'";
```

### Containers

There are no operators for containers: the standard `==` and `!=`
operators would be selected, and they return a plain `bool`, so a
failed check could not show the containers. Use `eq()` and `ne()`,
which compare the containers with the standard operators, and show
their elements when the check fails. The containers must be of the
same type, as for the standard operators:

```cpp
t.expect (mt::eq (std::vector<int>{ 1, 2 }, std::vector<int>{ 1, 2 }))
    << "vector{ 1, 2 } eq vector{ 1, 2 }";
```

### Other standard types

The function comparators also accept the scoped enumerations
(including `std::byte`), and the `std::pair`, `std::tuple`, and
`std::optional` objects, so also the maps, whose elements are pairs.
When a check fails, they are shown as follows:

- a scoped enumeration by its underlying value, with the suffix of its
  type, for example `1` for `int` and `1uc` for `std::byte`, whose
  underlying type is `unsigned char`; to show the names of the
  enumerators instead, define an `operator<<` for the enumeration, as
  for the [custom types](#custom-types);
- a pair or a tuple as `(a, b)`, and a map as `{(1, 2), (3, 4)}`;
- an optional by its value, or as `nullopt` when it has no value.

```cpp
enum class colour { red, green };

t.expect (mt::eq (paint (), colour::red)) << "colour is red";
t.expect (mt::ne (find (42), std::nullopt)) << "42 is found";
```

### Literals and wrappers

To convert constants into recognised typed operands, the following
literal operators are available in the separate `literals` namespace:

```cpp
namespace literals {
  auto operator""_i (); // int
  auto operator""_s (); // short
  auto operator""_c (); // char
  auto operator""_sc (); // signed char
  auto operator""_l (); // long
  auto operator""_ll (); // long long
  auto operator""_u (); // unsigned
  auto operator""_uc (); // unsigned char
  auto operator""_us (); // unsigned short
  auto operator""_ul (); // unsigned long
  auto operator""_ull (); // unsigned long long
  auto operator""_i8 (); // int8_t
  auto operator""_i16 (); // int16_t
  auto operator""_i32 (); // int32_t
  auto operator""_i64 (); // int64_t
  auto operator""_u8 (); // uint8_t
  auto operator""_u16 (); // uint16_t
  auto operator""_u32 (); // uint32_t
  auto operator""_u64 (); // uint64_t
  auto operator""_f (); // float
  auto operator""_d (); // double
  auto operator""_ld (); // long double
  auto operator""_b (const char* name, std::size_t size); // named bool, true
}
```

The integer literals follow the C++ syntax: decimal, hexadecimal (`0x10_i`),
binary (`0b101_i`), and octal (`010_i`, which is 8), with digit separators
(`1'000_i`). A decimal point, an exponent, or a value that does not fit in the
type of the literal (e.g. `300_u8`) is a compilation error.

Negative values are written with the unary minus (`-42_i`), which keeps the
type of the literal (`-1_i8` is an `int8_t`); the minimum of a signed type can
be written too (`-128_i8`). As in C++ for `unsigned int`, the negation of an
unsigned literal wraps around (`-1_u8` is 255). The negation of the minimum of
a signed type (`-(-128_i8)`) is a compilation error.

The floating-point literals are written with decimal digits and a decimal
point, optionally with digit separators (`1'000.000'5_d`), but without an
exponent; they can have up to 19 digits before the decimal point and 18
after it, otherwise the compilation fails.

The floating-point literals (`1.5_d`) and wrappers (`mt::to_d{ 1.5 }`)
compare with a tolerance of one unit of the last decimal written (0.1 for
`1.5`), so that `1.45 == 1.5_d` is true. All six comparisons apply it
consistently: values within the tolerance are equal, and neither less nor
greater. For the wrappers, the decimals are counted from the run-time
value, ignoring differences below 1e-7 caused by its binary
representation, so `mt::to_d{ 0.011 }` has a tolerance of 0.001; the
leading zeros of a small value are counted, so `mt::to_d{ 1e-12 }` has a
tolerance of 1e-12, and a zero (`mt::to_d{ 0.0 }`) has no decimals, so
it compares exactly. Whole values count as one decimal, as `42.0_d`, so
`mt::to_d{ 42.0 }` has a tolerance of 0.1.
Plain floating-point values compare exactly. To set the tolerance
explicitly, independent of how the value is written, use `mt::approx()`:

```cpp
t.expect (mt::eq (compute_float (), mt::approx (42.0f, 0.001f)));
```

The `_b` literal creates a named boolean constant, with the value `true`,
which is reported by its name instead of its value; it gives a name to a
flag in the failure messages:

```cpp
t.expect (mt::eq ("feature_enabled"_b, is_feature_enabled ()));
// When it fails: feature_enabled == false
```

With the operators in the `operators` namespace, `"feature_enabled"_b ==
is_feature_enabled ()` is reported in the same way; without them, the
comparison is a plain `bool` expression, and its operands are not
reported.

Similarly, for dynamic values, wrappers are provided to convert them into
recognised types:

```cpp
  using to_b = detail::value<bool>;
  using to_c = detail::value<char>;
  using to_sc = detail::value<signed char>;
  using to_s = detail::value<short>;
  using to_i = detail::value<int>;
  using to_l = detail::value<long>;
  using to_ll = detail::value<long long>;
  using to_u = detail::value<unsigned>;
  using to_uc = detail::value<unsigned char>;
  using to_us = detail::value<unsigned short>;
  using to_ul = detail::value<unsigned long>;
  using to_ull = detail::value<unsigned long long>;
  using to_i8 = detail::value<std::int8_t>;
  using to_i16 = detail::value<std::int16_t>;
  using to_i32 = detail::value<std::int32_t>;
  using to_i64 = detail::value<std::int64_t>;
  using to_u8 = detail::value<std::uint8_t>;
  using to_u16 = detail::value<std::uint16_t>;
  using to_u32 = detail::value<std::uint32_t>;
  using to_u64 = detail::value<std::uint64_t>;
  using to_f = detail::value<float>;
  using to_d = detail::value<double>;
  using to_ld = detail::value<long double>;

  // Template for wrapping any other type.
  template <class T>
  struct to_t : detail::value<T>
  {
    constexpr explicit to_t (const T& t) : detail::value<T>{ t }
    {
    }
  };
```

Refer to the [Literals and Wrappers](/docs/api/groups/micro-os-plus-micro-test-plus-literals/) reference page.

### Functions vs. Operators and Literals

Both comparator functions (e.g. `eq()`) and overloaded operators (e.g. `==`) are fully supported; the choice is largely a matter of personal preference.

**Comparator functions** guarantee that the actual values are always displayed when an expectation fails, and their syntax is explicit and unambiguous.

**Overloaded operators** are more immediately familiar to most C++ developers, but require at least one operand to be of a specific typed wrapper or literal type (e.g. `42_i`); without this, the actual values will not be reported on failure.

:::info
The µOS++ projects favour the use of explicit comparator functions.
:::

### Utility functions

```cpp
namespace utility {
  bool is_match (std::string_view input, std::string_view pattern);
}

namespace utility {
  template <class T, class Delim_T>
  auto split (T input, Delim_T delim) -> std::vector<T>;
}
```

### Custom Types

The function comparators also accept **user-defined types**, provided
that the type has the operator used by the comparator: `operator==` for
`eq()` and `ne()` (in C++20, `operator==` also provides `!=`), and
`operator<=>` (or the individual relational operators) for `lt()`,
`le()`, `gt()`, and `ge()`.

Since the comparators **report the values** of their operands when a
check fails, they also need to know how to print the type. For this, the
application must define an `operator<<` that writes the value to an
`mt::expression_formatter`, in the namespace of the type, so that it is
found by argument-dependent lookup. Without it, the comparators do not
compile for that type; only the scoped enumerations are shown without
it, by their underlying value.

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

namespace app
{
  struct point
  {
    int x;
    int y;
  };

  constexpr bool
  operator== (const point& lhs, const point& rhs)
  {
    return lhs.x == rhs.x && lhs.y == rhs.y;
  }

  // Used to report the values of failed checks.
  inline mt::expression_formatter&
  operator<< (mt::expression_formatter& formatter, const point& p)
  {
    return formatter << "{ " << p.x << ", " << p.y << " }";
  }
} // namespace app

int
main (int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise (argc, argv);

  ts.test ("Points", [] (auto& t) {
    app::point p{ 1, 2 };
    t.expect (mt::eq (p, app::point{ 1, 3 })) << "point is { 1, 3 }";
  });

  return tr.run ();
}
```

The failed check reports both values:

```console
        not ok 1 - point is { 1, 3 }
          ---
          condition: "{ 1, 2 } == { 1, 3 }"
          at:
            filename: main.cpp
            line: 35
          ...
```

The formatter accepts the standard arithmetic types, characters,
strings, pointers, containers, scoped enumerations, pairs, tuples, and
optionals, so the members can usually be written
directly, as above. The `char` pointers and arrays, also when not
`const`, are written as strings (a null pointer as `nullptr`); the other
pointers, including the `signed char` and `unsigned char` (`uint8_t`)
pointers, are written as addresses. A plain boolean check, such as
`t.expect (p == q)`, needs no formatter, but on failure it reports only
the source location.

### Test suites

Test suites are named sequences of test cases.

#### Static test suites

In the common use case, test suites are static instances of the `static_suite`
class, which automatically register themselves with a static instance of the
`runner`.

The main program looks like this:

```cpp
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

mt::runner sr;

int
main (int argc, char* argv[])
{
  auto& ts = sr.initialise (argc, argv, "Top suite");

  // ... possible top suite tests ...

  return sr.run ();
}
```

Each test suite resides in a separate source file, for example:

```cpp
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

extern mt::runner sr;

static void
suite_function (mt::suite& ts)
{
  ts.test ("Check various conditions", [] (auto& t)
    {
      t.test ("Check truth", [] (auto& t) {
        t.expect (true);
      });
    });
}

static mt::static_suite suite = { "Static suite", sr, suite_function };
```

The implementation uses the C++ static constructors that are performed before the `main()` function is called. The order of registration is not defined; to provide a certain degree of predictability, the framework runs all suites when the `run()` method is called, after **ordering them by name**.

#### Non-static test suites

Static test suites are just a convenience, since they automatically register themselves with the runner, and not including the source file with the test suite in the build automatically disables the tests.

However they are not mandatory, test suites can be manually added to the
runner.

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

extern void
suite_function (mt::suite& ts);

int
main(int argc, char* argv[])
{
  mt::runner tr;

  auto& ts = tr.initialise(argc, argv, "Minimal");

  ts.test ("Check truth", [] (auto& t) {
    t.expect (true);
  });

  tr.suite("External suite", suite_function);

  return tr.run ();
}
```

The suites must be added before `run()` is called. A suite added while
`run()` runs, for example from the body of another suite, or after it
returned, would never run; it is rejected, the error is reported on
`stderr`, and the result is not 0.

#### Example

An even more elaborate example from a real-world project is:

```cpp
namespace os = micro_os_plus;
namespace mt = micro_os_plus::micro_test_plus;

// Define a function template to run the tests.
template <class T>
void
check_double_list_links (mt::suite& ts)
{
  static T left_links;
  static T links;
  static T right_links;

  ts.test ("Initial", [&] (auto& t) {
    if constexpr (T::is_statically_allocated::value)
      {
        // Check if the node is cleared.
        t.expect (mt::eq (links.previous (), nullptr)) << "prev is null";
        t.expect (mt::eq (links.next (), nullptr)) << "next is null";
        t.expect (links.uninitialized ()) << "uninitialised";

        left_links.initialize ();
        links.initialize ();
        right_links.initialize ();
      }

    t.expect (!left_links.linked ()) << "left unlinked";
    t.expect (!links.linked ()) << "unlinked";
    t.expect (!right_links.linked ()) << "right unlinked";
  });

  ts.test ("Link", [&] (auto& t) {
    // Link left as previous.
    links.link_previous (&left_links);

    // Link right as next.
    links.link_next (&right_links);

    // The node must now appear as linked.
    t.expect (links.linked ()) << "linked";

    t.expect (mt::eq (left_links.next (), &links)) << "left linked";
    t.expect (mt::eq (right_links.previous (), &links)) << "right linked";
  });

  ts.test ("Unlink", [&] (auto& t) {
    // Unlink the central node.
    links.unlink ();
    t.expect (!links.linked ()) << "unlinked";

    // Left and right must indeed point to each other.
    t.expect (mt::eq (left_links.next (), &right_links)) << "left -> right";
    t.expect (mt::eq (right_links.previous (), &left_links)) << "right <- left";
  });

  if constexpr (!T::is_statically_allocated::value)
    {
      ts.test ("Allocated on stack", [] (auto& t) {
        T stack_links;
        t.expect (!stack_links.linked ()) << "unlinked";
      });
    }
}

// Instantiate the test for statically allocated lists.
static mt::static_suite ts_static_double_list_links
    = {
        "Static double list links", sr,
        check_double_list_links<os::utils::static_double_list_links>
      };

// Instantiate the same test for regular lists.
static mt::static_suite ts_double_list_links
    = { "Double list links", sr,
        check_double_list_links<os::utils::double_list_links> };
```

Refer to the [Test Suites](/docs/api/groups/micro-os-plus-micro-test-plus-test-suites/) reference page.

### Explicit Namespaces

In complex projects, the definitions within the
`micro_test_plus` namespace may conflict with those of the application.

:::info
To avoid naming conflicts, it is advisable to use comparator functions with explicit namespaces.
:::

For those who favour brevity, it is also possible to declare a short alias for the `micro_os_plus::micro_test_plus` namespace at the appropriate scope and prefix all references with it.

```cpp
namespace mt = micro_os_plus::micro_test_plus;

{
  // ...

  ts.test ("Check answer", [] (auto& t) {
    t.expect (mt::eq (compute_answer (), 42)) << "answer is 42";
  });
}
```

### Memory Footprint

The memory footprint of unit tests based on µTest++ is generally smaller than that of traditional C++ testing frameworks, primarily because the `iostream` library is not utilised.

For example, for Cortex-M7F, the minimal test, which includes the complete functionality, requires less than 110 KB:

```
   text    data     bss     dec     hex filename
 105552    2280    3184  111016   1b1a8 minimal-test.elf
```

<details>
<summary>A similar test using [Boost UT](https://boost-ext.github.io/ut/) produced a binary over 400 KB in size.</summary>

The equivalent minimal test was:

```cpp
#include <boost/ut.hpp>

int
main(int argc, char* argv[])
{
  using namespace boost::ut;

  "Check truth"_test = [] {
    expect(true);
  };

  return 0;
}
```

```text
   text    data     bss     dec     hex filename
 410200    4452   10556  425208   67cf8 ut-minimal-test.elf
```

</details>

However, the use of templates for implementing comparators and operators
should be used with care on platforms with severely limited memory
resources, as each unique pair of operand types contributes to the overall
programme size.

If necessary, µTest++ can be used without custom comparators and operators,
relying solely on standard boolean expressions, while still providing the
essential functionality for testing conditions. In this configuration, the
actual values compared are not displayed on failure.

:::info
The memory footprint in `debug` builds (compiled with `-O0`) is significantly larger than in `release` builds. If required, the optimisation level for the `debug` build may be increased to `-Og` to conserve memory.
:::

### Timings

On native platforms that support a standard way of accessing the system clock (such as the POSIX `clock_gettime()`), the µTest++ runner measures the time spent in each test suite and reports it in milliseconds alongside the results.

For example:

```
ok 1 - Minimal # { test suite passed, 1 check in 1 test case, time: 0.007 ms }
1..1
# { total: 1 check passed, 0 failed, in 1 test case, 1 test suite, time: 0.030 ms }
```

On embedded platforms using Arm semihosting, the clock resolution is in the range of tens of milliseconds — too coarse for meaningful reporting — and timings are therefore omitted from the output.

### Console output

The reporters write all console output through the standard `stdout`
stream, using `vfprintf()`, `fputs()`, and `fflush()`. Output written
by the tests with `printf()` shares the same stream and buffer, so the
two appear in the expected order.

On embedded platforms, where the output is usually forwarded to the host
via semihosting, a serial port, or a debug channel, the platform must
route `stdout` and `printf()`/`puts()`/`putchar()` to the same
destination. Platforms that redirect only `printf()` (for example via
`-Wl,--wrap=printf`) to a separate channel may interleave the test and
reporter output out of order.

## C API

Whilst µTest++ can be used to test C code, its implementation relies
extensively on modern C++ features that cannot be replicated in C.

Consequently, there are no C equivalents for the C++ definitions provided
by µTest++.

## Command line options

### Verbosity

By default, µTest++ displays only **test case summaries for passing tests** (for failed tests, all expectations are shown).

To adjust the verbosity, one of the following command-line options may be specified:

- `--verbose` – display **all expectations**, irrespective of their outcome
- `--quiet` – display only the **runner totals**; the TAP reporter also displays one `ok`/`not ok` line per test suite, with the plan counting them, so that the output remains a valid TAP document, which node-tap and the other TAP consumers read as failed when a suite failed
- `--silent` – suppress all output and return **solely the exit code**

When exceptions are not enabled and a failed requirement aborts the test
execution, the results of the aborted test case are displayed also with
`--quiet`, since the totals are never reached; see
[Aborting the test execution](#aborting-the-test-execution).

Refer to the [Command Line Options](/docs/api/groups/micro-os-plus-micro-test-plus-cli/) reference page.

### Filter

To run only some of the test suites and test cases, select them by name with the `--filter` option, as with `--grep` in node-tap. The option may be repeated, one pattern per nesting level: the first pattern applies to the suite names, the second to the test case names, and each further one to the nested test cases.

```sh
sample-test --filter='Args*|*namespace*'
sample-test --filter='*' --filter='Check one'
```

In a pattern, `*` matches any sequence of characters, `?` matches any single character, and `|` separates alternatives; the match is case-sensitive, and the pattern must cover the whole name. The suites and test cases that do not match are not run, and are reported as skipped (`ok 2 - Args suite # SKIP filtered` in TAP); the totals lines show how many were skipped.

The top suite is never skipped as a whole, since its body is `main()`, but its test cases are filtered like those of any other suite.

### Output file

To also write the report to a file, use the `--output-file` option, either as `--output-file=<path>` or as `--output-file <path>`.

The two outputs have different purposes: the console is intended for the people who watch the tests run, and its content is selected with the verbosity options, while the output file is intended for the integration with other tools (for example a CI pipeline, or a TAP consumer such as node-tap).

- With the **TAP** reporter (the default), the output file always receives the **complete report**, whatever the console verbosity; this is the reporter to use for integration.
- The **human** reporter is intended for the console. Its output file receives the complete report only with the normal or verbose verbosity; with `--quiet` or `--silent`, the file is incomplete (it contains the test case names, and, with `--quiet`, the totals), and should not be relied upon.

### The _human_ reporter

Starting with v4.x, the default reporter is **TAP**. For compatibility with
previous versions, the original **human** reporter was preserved and can be
enabled with:

```
--reporter human
```

The output is slightly more compact, for example:

```
µTest++ human report

• Minimal

    ✓ Check various conditions - passed (2 checks)

✓ Minimal - passed (2 checks in 1 test case), time: 0.025 ms

✓ Total: 2 checks passed, 0 failed, in 1 test case, 1 test suite, time: 0.082 ms
```

The human reporter is intended for reading the console output. For the integration with other tools, use the TAP reporter, whose output file is always complete (see [Output file](#output-file)).
