## Rationale

At its most basic level, the simplest testing approach requires no framework at all.
A test for a C or C++ project can readily be written without any framework,
perhaps utilising the standard `assert()` macro or a similar user-defined mechanism.

However, with this mechanism, failed assertions typically abort the test, and when dealing with multiple
test cases containing numerous checks, it is **preferable to obtain a comprehensive report**.

Testing frameworks address this need by providing convenient mechanisms for writing
various checks and generating clear, structured reports.

The xPack Framework already includes ready-to-use
support for several testing frameworks
([Google Test](https://github.com/xpack-3rd-party/googletest-xpack),
[Catch2](https://github.com/xpack-3rd-party/catch2-xpack),
[Boost UT](https://github.com/xpack-3rd-party/boost-ut-xpack)).
Nevertheless, these frameworks tend to be quite demanding in terms of memory resources, and
the learning curve required to master them can be rather steep.

Therefore, for embedded projects, a **simpler solution** with a **smaller
memory footprint** was considered a valuable addition.

## Overview

The initial version of the **µTest++ Testing Framework** drew its primary inspiration from
[Node TAP](https://node-tap.org), with a strong emphasis on simplicity. Version 3.x was heavily influenced by [Boost UT](https://boost-ext.github.io/ut/), from which it derived its function comparators,
while version 4.x represented a complete redesign, drawing even more inspiration from
[Node TAP](https://node-tap.org) by passing explicit references to parent objects into test and suite callbacks.

## Concepts and features

- For more complex applications, test cases may be organised into test suites.
- Test suites can reside in separate compilation units and automatically register themselves with the test runner.
- A **test suite** is a named collection of test cases.
- A **test case** comprises a sequence of **test conditions** (also referred to as **tests** or **checks**), which are expectations or requirements — conditions anticipated to be true.
- Tests are based on logical expressions, typically evaluating a result and comparing it to an expected value.
- For C++ projects, it is also possible to verify whether evaluating an expression results in an **exception** being thrown.
- Each test either passes or fails.
- For **expectations**, the runner maintains a count of occurrences.
- **Requirements** are critical conditions that must be satisfied for the test case to proceed.
- A failed requirement stops the current test case; the run continues with the next one.
- Test progress is displayed on STDOUT, with each test on a separate line, prefixed by an indication of whether the test passed or failed.
- Failed tests indicate the location within the file and, where possible, the actual values used in the evaluation.
- The primary result of the test is returned to the system as the process exit code.
- Optionally, the detailed test results can be written to a separate file, for example in TAP format.

A test suite is deemed successful if there are no failed tests.

If all test suites are successful, the process returns an exit value of 0.

## Getting started

### Minimal test

The most basic test comprises a single test case with a single expectation; for example:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

// For convenience, alias the fully qualified namespace to a shorter name.
namespace mt = micro_os_plus::micro_test_plus;

int
main(int argc, char* argv[])
{
  // Create a local instance of the runner. Name the top suite.
  mt::runner tr;

  // Initialise the runner and get a reference to the top suite.
  auto& ts = tr.initialise(argc, argv, "Minimal");

  // Perform a simple test, with a single expectation.
  ts.test ("Check truth", [] (auto& t) {
    t.expect (true);
  });

  return tr.run ();
}
```

:::info C++ Lambdas
The second argument passed to the `test()` function is a **C++ lambda**, which is an unnamed inline function.

µTest++ recommends using lambdas whenever possible, but also supports passing any C++ callable object, such as pointers to functions, functors, `std::function`, etc.
:::

### TAP output

By default, when a test is executed, the output conforms to the **TAP14 (Test Anything Protocol version 14)** [specification](https://testanything.org/tap-version-14-specification.html), a well-established protocol for communication between tested logic and test harnesses.

For the above test, the verbose output would look like:

```console
TAP version 14
# Subtest: Minimal
    # Subtest: Check truth
        ok 1 - true
        1..1
    ok 1 - Check truth # { test case passed, 1 check }
    1..1
ok 1 - Minimal # { test suite passed, 1 check in 1 test case, time: 0.007 ms }
1..1
# { total: 1 check passed, 0 failed, in 1 test case, 1 test suite, time: 0.030 ms }
```

In the `ok`/`not ok` lines, the names of the suites and test cases, the messages, and the expressions are escaped as the specification recommends: each `#` is written as `\#`, and each `\` as `\\`, so that a `#` in a name (for example `parser # TODO rework`) is not read as a `TODO` or `SKIP` directive, which would hide a failure; the TAP consumers remove the escapes. The line breaks are replaced by spaces, so that a name or a message always fits on its line. The `# Subtest:` lines, which are comments, show the names as they are, with only the line breaks replaced.

### Testing a computed value

A slightly more practical example would verify the result of a computed value; for instance:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

static int
compute_answer()
{
  return 42;
}

int
main(int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise(argc, argv, "The Answer");

  ts.test ("Check answer", [] (auto& t) {
    t.expect (compute_answer() == 42) << "answer is 42";
  });

  return tr.run ();
}
```

```console
TAP version 14

# Subtest: The Answer
    # Subtest: Check answer
        ok 1 - answer is 42
        1..1
    ok 1 - Check answer # { test case passed, 1 check }
    1..1
ok 1 - The Answer # { test suite passed, 1 check in 1 test case, time: 0.007 ms }
1..1
# { total: 1 check passed, 0 failed, in 1 test case, 1 test suite, time: 0.030 ms }
```

If the function returns an incorrect value, the test will fail; for example:

```cpp
static int
compute_answer()
{
  return 42 + 1;
}
```

In this case, the test output will be as follows:

```console
TAP version 14

# Subtest: The Answer

    # Subtest: Check answer
        not ok 1 - answer is 42
            ---
            at:
              fileName: main.cpp
              lineNumber: 17
            ...
        1..1
    not ok 1 - Check answer # { test case FAILED, 0 checks passed, 1 failed }
    1..1
not ok 1 - The Answer # { test suite FAILED, 0 checks passed, 1 failed, in 1 test case, time: 0.039 ms }
1..1
# { total: 1 check passed, 1 failed, in 1 test case, 1 test suite, time: 0.077 ms }
```

The output identifies the failed test at line 17, but does not provide further details, such as the actual incorrect value.

### More advanced comparators

To obtain a more informative report, such as the actual incorrect value, the test should be slightly more detailed and employ a function comparator; for example:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

static int
compute_answer()
{
  return 42+1;
}

int
main(int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise(argc, argv, "The Answer");

  ts.test ("Check answer with comparator", [] (auto& t) {
    t.expect (mt::eq (compute_answer (), 42)) << "answer is 42";
  });

  return tr.run ();
}
```

The output would be:

```console
TAP version 14

# Subtest: The Answer

    # Subtest: Check answer with comparator
        not ok 1 - answer is 42
            ---
            expect: 43 == 42
            at:
              fileName: main.cpp
              lineNumber: 69
            ...
        1..1
    not ok 1 - Check answer with comparator # { test case FAILED, 0 checks passed, 1 failed }
    1..1
not ok 1 - The Answer # { test suite FAILED, 0 checks passed, 1 failed, in 1 test case, time: 0.036 ms }
1..1
# { total: 0 checks passed, 1 failed, in 1 test case, 1 test suite, time: 0.067 ms }
```

Here, `eq()` is a **function comparator**, a function not only capable of comparing almost any type but also of recording the values of its operands. Similar functions exist for all types of comparisons (`ne()`, `lt()`, `le()`, `gt()`, `ge()`, and `approx()`).

The earlier releases also offered overloaded operators, literals (such as `42_i`), and type wrappers (such as `mt::to_i`); they are deprecated, in favour of the function comparators (see [Deprecated operators, literals, and wrappers](#deprecated-operators-literals-and-wrappers)).

### More complex tests

For simple scenarios, invoking multiple test cases in `main()` may suffice.

For more complex applications, test cases can be grouped into test suites and invoked, potentially multiple times with different arguments (see the [Test suites](#test-suites) section).

## C++ API

### Namespaces

The definitions are organised within several namespaces under `micro_os_plus`:

- `micro_os_plus::micro_test_plus` (commonly aliased as `mt`)
- `micro_os_plus::micro_test_plus::operators` (deprecated)
- `micro_os_plus::micro_test_plus::literals` (deprecated)
- `micro_os_plus::micro_test_plus::utility`

`micro_os_plus` is the primary µOS++ namespace, and `micro_test_plus` is the
namespace for µTest++.

The `operators` namespace provides custom operators, while the `literals`
namespace defines user-defined literals (such as `1_i`); both are deprecated
since 5.1.0.

### Test runner

The test framework is implemented as a runner object, which must be instantiated and initialised.

#### Instantiation

The runner object must be instantiated by the application:

```cpp
mt::runner tr;
```

For simple tests, the runner can be a local stack-allocated object in `main()`.

#### Initialisation

After instantiation, the runner **must** be initialised, usually by passing the main arguments and the name of the top default suite:

```cpp
auto& ts = tr.initialise(argc, argv, "Main");
```

The `initialise()` member function returns the default top suite, which is required later to create test cases.

On platforms without a command line, such as embedded applications without semihosting arguments, the runner can be initialised with the options set directly, starting from the defaults, instead of the main arguments:

```cpp
mt::runner_options options{};
options.selected_reporter = mt::reporter_kind::human;
options.verbosity_level = mt::verbosity::verbose;

auto& ts = tr.initialise(options, "Main");
```

The members of `runner_options` correspond to the command-line options: `selected_reporter` to `--reporter`, `verbosity_level` to `--silent`, `--quiet`, and `--verbose`, `output_file_path` to `--output-file`, `colour` to `--color` (or `--use-colour`), `filter_patterns` to `--filter`, and `list_tests` to `--list-tests` (or `--list`).

#### Test result

To run the registered suites, end the session, and return the test result as the process exit code, the runner provides the `run()` member function; the session runs only once, and later calls return the same result:

```cpp
return tr.run ();
```

The result is 0 if all checks passed, and 1 otherwise, including when a suite was added too late (see [Non-static test suites](#non-static-test-suites)). If the command-line options, or the `runner_options`, were not valid (an unknown reporter name, an unknown colour mode, a missing option argument, or an output file that cannot be opened), the error is reported on `stderr` when the runner is initialised, the option is ignored, and the tests are still run, but the result is 2.

#### Aborting the test execution

When exceptions are not enabled, a failed requirement cannot stop only its test case (see [Requirements](#requirements)), so it aborts the whole test execution: the remaining test cases and suites do not run, `run()` does not return, and no totals are written. The test execution can also be aborted explicitly, from a test case, from a suite, or from the application, by calling `tr.abort ()`. Before the process is terminated, the reporter completes the report, in place of the totals:

1. it displays the results of the running test case, if any; after a failed requirement, they end with it, and the human reporter marks it as `test execution aborted` (the TAP reporter adds no marker, since its `Bail out!` line, below, reports the abort); they are preceded by the name of the test case, and by those of the outer test cases, unless already displayed, so that a failure cannot be attributed to the previous test case;
2. it ends the output with a line with the location of the failed requirement, or of the `abort()` call: `✗ Test execution aborted at <file>:<line>` for the human reporter, and `Bail out! Requirement failed at <file>:<line>` (or `Bail out! Test execution aborted at <file>:<line>`, for an explicit abort) for the TAP reporter, which tells the TAP consumers that the run stopped early, not that the output was truncated.

Then `runner::abort()` flushes the standard streams, calls the abort handler, if one was set (see below), and then `::abort()`. An abort before `initialise()`, or after `run()`, when there is no report to complete, is reported on `stderr`, as `error: test execution aborted at <file>:<line>`.

With `--quiet`, which otherwise displays only the failed checks and the totals, the failed checks of the aborted test case are displayed as well, since the totals are never reached. With `--silent`, nothing is displayed. If an output file is used, the results and the final line are written to it too, whatever the verbosity.

For example, with the human reporter, the end of the output is:

```
    ✓ Check various conditions - passed (2 checks)

    • Parse configuration
        ✓ file found
        ✗ sections parsed FAILED (main.cpp:42, 0 > 0) - test execution aborted

✗ Test execution aborted at main.cpp:42
```

and with the TAP reporter:

```
    # Subtest: Parse configuration
        ok 1 - file found
        not ok 2 - sections parsed
          ---
          condition: "0 > 0"
          at:
            fileName: main.cpp
            lineNumber: 42
          ...
Bail out! Requirement failed at main.cpp:42
```

An explicit abort is intended for the failures after which running the other tests is pointless, or even harmful, whether exceptions are enabled or not: for example, when the device or the environment that all the tests use cannot be initialised. Unlike a failed `require()` with exceptions, which stops only its test case, `tr.abort ()` always stops the whole test execution. The runner must be reachable from the test case, for example captured by reference:

```cpp
ts.test ("Open the device", [&tr] (auto& t)
  {
    t.expect (device.open ()) << "device opened";
    if (!device.is_open ())
      {
        // No other test can run without the device.
        tr.abort ();
      }
  });
```

With the TAP reporter, the end of the output is then:

```
    # Subtest: Open the device
        not ok 1 - device opened
          ---
          at:
            fileName: main.cpp
            lineNumber: 57
          ...
Bail out! Test execution aborted at main.cpp:61
```

Unless the abort handler ends the program otherwise, the process ends with `SIGABRT`, so a test harness sees a terminated process, not an exit code returned by `run()`.

On embedded targets, where terminating the process is not meaningful, the application can set a handler, called before `::abort()`, for example to reset the target or to signal the result to the debugger:

```cpp
tr.set_abort_handler ([] (const mt::reflection::source_location& sl)
  {
    // Signal the failure, then reset the target; do not return.
  });
```

If the handler returns, `::abort()` is still called.

When exceptions are enabled, the handler may also throw an exception, to return control to the application without terminating the process, for example when the test runner is only one part of a larger program. The test cases and the suites do not catch it, as they do with the other exceptions, so it leaves `run()`, or the `test()` call that started a test case of the top suite, and reaches the application:

```cpp
struct test_aborted {};

tr.set_abort_handler ([] (const mt::reflection::source_location&)
  { throw test_aborted{}; });

int result;
try
  {
    result = tr.run ();
  }
catch (const test_aborted&)
  {
    result = 3; // The report is already complete.
  }
```

The abort is final: the report is complete, no test case runs afterwards, and `initialise()` and `run()` report an error on `stderr` (`run()` returns 1). Without exceptions, the handler must not return.

Refer to the [Test Runners](/docs/api/groups/micro-os-plus-micro-test-plus-runners/) reference page.

### Test cases

Test cases are collections of checks to be executed within the same environment.

Test case objects can be created using the `test()` member function provided by the test suite object:

```cpp
template <typename Callable_T, typename... Args_T>
void test (const test_case_name& name, Callable_T&& func, Args_T&&... arguments);
```

The name is a string literal, a `const char*`, or a `std::string`,
converted implicitly to `test_case_name`, which also records the
location of the `test()` call. The name is not copied; since the test
case runs within the call to `test()`, a temporary string, such as
`prefix + " overflow"`, can be passed. A `std::string_view` is not
accepted, since it may not be null-terminated; pass
`std::string (view)` instead.

A helper function that adds test cases on behalf of its caller can take
a `const mt::test_case_name&` parameter and pass it to `test()`, so that
the location reported for the test case is that of the call to the
helper:

```cpp
void
check_answer (mt::suite& ts, const mt::test_case_name& name, int value)
{
  ts.test (name, [value] (auto& t) { t.expect (mt::eq (value, 42)); });
}
```

The additional arguments, if any, are passed to the callable after the
test case reference. They are copied when `test()` is called, as they
are by `runner::add_suite()` and by the `static_suite` constructor, whose
suites run later, so a reference parameter refers to the copy. To
refer to the caller's object, pass a pointer, or `std::ref (object)`
for a parameter of type `T&`. A lambda can also capture the values
instead.

When exceptions are enabled, an exception that escapes the body of a
test case is reported as a failed check of that test case, at the
location of the `test()` call, and the run continues with the next test
case; the message includes the result of `what()` for a
`std::exception`:

```console
    • Parse configuration
        ✓ header is valid
        ✗ unexpected exception: invalid key FAILED (config.cpp:42)
    ✗ Parse configuration - FAILED (1 check passed, 1 failed)
```

Similarly, an exception that escapes the body of a test suite, outside
its test cases (for example from a set-up step), is reported as a
failed check of that suite, after the test cases already run; the
rest of the suite body is skipped, and the run continues with the next
suite. Since the suites do not record a source location, none is
shown:

```console
• Configuration suite

    ✓ Parse configuration - passed (1 check)

    ✗ unexpected exception in the suite body: no such file FAILED
✗ Configuration suite - FAILED (1 check passed, 1 failed, in 1 test case)
```

For the exception to reach the framework, the body, of a test case or
of a test suite, must not be declared `noexcept`; otherwise the
exception calls `std::terminate()`, and ends the program.

Refer to the [Test Cases](/docs/api/groups/micro-os-plus-micro-test-plus-test-case/) reference page.

### Expectations and requirements

Expectations and requirements are checks that evaluate expressions
yielding boolean values; they differ in what happens after a failure.

Both are created with member functions of the test case objects, and return an
object to which a message can be appended with `<<`; the check is
reported at the end of the statement:

```cpp
template <class Expr_T>
  requires extension::checkable<Expr_T>
auto expect (const Expr_T& expr);

template <class Expr_T>
  requires extension::checkable<Expr_T>
auto require (const Expr_T& expr);
```

The expression is either a framework expression (a comparator, an
operator, or a logical function), whose operands are reported on
failure, or any value that the condition of an `if` statement accepts,
including the types with an `explicit operator bool`, such as
`std::optional`, `std::unique_ptr`, and `std::function`:

```cpp
auto buffer = std::make_unique<std::byte[]> (size);
t.require (buffer) << "buffer allocated";
```

A failed **expectation** is reported and counted, and the test case
continues, so that all its checks are evaluated and reported in one run.

The message accepts the same values as the operands of the
[function comparators](#function-comparators), including the
[custom types](#custom-types) with an `operator<<` for the formatter,
and any number of them can be appended. They are written as in the
reports of the comparators, except that the numbers have no type
suffixes and the `char` values are not quoted, since the message is
text; the wide characters (`u'x'`, `U'x'`, `L'x'`) are written as in the
reports, since they cannot be appended to the text unchanged:

```cpp
t.expect (mt::eq (parse (input), expected))
    << "input " << input << ", " << input.size () << " bytes";
```

A part of the message that is valid only after a failure can be given
as a callable object, such as a lambda, that returns a value accepted
by the message; it is called only if the check fails, and its result is
appended, while after a success it appends nothing:

```cpp
std::expected<config, std::string> result = parse ("config.json");
t.require (result.has_value ())
    << "parse failed: " << [&result] { return result.error (); };
```

The function pointers are not called; they are written as addresses.

#### Requirements

A failed **requirement** is reported and counted as a failed
expectation, and then the rest of the test case is skipped, since the
following checks would be meaningless; the run continues with the next
test case:

```cpp
ts.test ("Parse configuration", [] (auto& t)
  {
    auto config = parse ("config.json");
    t.require (config.has_value ()) << "configuration parsed";

    // Not reached if the configuration could not be parsed.
    t.expect (config->version == 2) << "version 2";
  });
```

A failed requirement in a nested test case stops only the nested test
case; the outer test case continues, and fails because of it.

The test case is stopped by throwing an exception, at the end of the
statement, after the message was appended. It is not derived from
`std::exception`, so a `catch (const std::exception&)` in the test case
body does not intercept it; a `catch (...)` does, and must rethrow it
with `throw;`. The test case body must not be `noexcept`, since the
exception would call `std::terminate()`.

The human reporter marks the failed requirement with
`- test case stopped`, after the location; the TAP reporter reports it
like any other failed check, as node-tap does, and the stop is shown by
the plan of the test case, which follows it:

```
    • Parse configuration
        ✗ configuration parsed FAILED (main.cpp:4) - test case stopped
```

Without exceptions (for example with `-fno-exceptions`, common on
embedded targets), the test case cannot be stopped, and a failed
requirement aborts the whole test execution, as described in
[Aborting the test execution](#aborting-the-test-execution): the
results of the test case are displayed, ending with the failed
requirement, but the remaining test cases do not run and no totals are
written.

`assume()` is a deprecated alias of `require()`. The name was
misleading: in JUnit and Hypothesis, an unmet assumption **skips** the
test, which is not counted as failed, while in µTest++ it fails it.

#### Comparison with other frameworks

The plain `assert()` macro, mentioned in the [Rationale](#rationale),
terminates the whole program at the first failure. Test frameworks
distinguish the non-fatal checks, which only report the failure, from
the fatal ones, which also stop the test; most of them stop only the
current test case, which is also the behaviour of `require()`:

| Framework | Non-fatal | Fatal | After a fatal failure |
| --- | --- | --- | --- |
| µTest++ | `expect()` | `require()` | the test case is stopped |
| GoogleTest | `EXPECT_*()` | `ASSERT_*()` | the current function returns |
| Catch2 | `CHECK()` | `REQUIRE()` | the test case is stopped |
| doctest | `CHECK()` | `REQUIRE()` | the test case is stopped |
| Boost.Test | `BOOST_CHECK()` | `BOOST_REQUIRE()` | the test case is stopped |
| Boost.UT | `expect()` | `expect (...) << fatal` | the program exits |
| Unity (C) | — | `TEST_ASSERT_*()` | the test is stopped |
| JUnit | — | `assert*()` | the test is stopped |
| C library | — | `assert()` | the program is aborted |

Some differences are worth noting:

- in GoogleTest, `ASSERT_*()` returns only from the function in which
  it is used; if this is a helper function, the test continues after
  the call;
- Catch2, doctest, and Boost.Test also stop the test case with an
  exception; without exceptions, Catch2 calls `std::terminate()`,
  and doctest either removes `REQUIRE()`, or makes it behave as
  `CHECK()`;
- Boost.UT reports the fatal failure and calls `std::exit()`, so the
  remaining tests do not run, as with the previous versions of
  `assume()`;
- Unity, a C framework, stops the test with `longjmp()`, which does not
  run the destructors of the C++ objects;
- in JUnit, an unmet `assume*()` aborts the test, which is reported as
  skipped, not as failed.

Refer to the [Expectations](/docs/api/groups/micro-os-plus-micro-test-plus-expectations/)
and [Requirements](/docs/api/groups/micro-os-plus-micro-test-plus-requirements/) reference pages.

### Nested test cases

Test cases can be defined in a nested manner, i.e., a test case can include not only checks, but also other test cases, at any nesting level.

A nested test case is created by calling `test()` on the outer test
case, and runs immediately; a failed nested test case also fails the
outer one:

```cpp
ts.test ("Parse configuration", [] (auto& t)
  {
    t.expect (parse ("config.json")) << "configuration parsed";

    t.test ("Defaults", [] (auto& nt)
      {
        nt.expect (default_port () == 80) << "default port";
      });
  });
```

A test case started on the suite, with `ts.test()`, from the body of a
running test case (for example via a captured suite reference), cannot
follow it in the report, since the running test case has not ended; it
runs nested in the innermost running test case, as if `t.test()` had
been called.

Each nesting level adds to the stack used by the test; see
[Stack usage](#stack-usage).

### Test cases for each value

The same test can be run for several values with `test_each()`, which
adds and runs a test case for each value, on the suite or, nested, on
a test case; the callable receives the test case and the value:

```cpp
ts.test_each ("Buffer sizes", { 1, 16, 512 }, [] (auto& t, int size)
  {
    t.expect (mt::eq (make_buffer (size).size (), size));
  });
```

The values may be a braced list, a range (a container, an array, a
span, or a view), or a tuple, whose values may have different types,
for a generic callable:

```cpp
ts.test_each ("Serialise", std::tuple{ 42, 1.5, "text" },
              [] (auto& t, const auto& value)
  {
    t.expect (mt::eq (deserialise (serialise (value)), value));
  });
```

Each test case is named after the common name, followed by the value
in parentheses, written as in the messages (`Buffer sizes (16)`,
`Serialise (text)`); a value that cannot be written, an application
type without an `operator<<`, is replaced by its position, starting at
1 (`Records (#2)`). The values are passed to the callable as copies,
as the arguments of `test()`.

### Function comparators

To facilitate clear reporting of differences between expected and
actual values in failed conditions, several **generic comparator functions**
are provided.

```cpp
template <class Lhs_T, class Rhs_T>
auto eq(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto ne(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto lt(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto le(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto gt(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T>
auto ge(const Lhs_T& lhs, const Rhs_T& rhs);

template <class Lhs_T, class Rhs_T, class Epsilon_T>
auto approx(const Lhs_T& lhs, const Rhs_T& rhs, const Epsilon_T& epsilon);
```

The C strings (`char` arrays, including the string literals, and `char`
pointers) are compared by content, also with `std::string` and
`std::string_view`, so `mt::eq (actual, "abc")` checks the characters,
not the addresses; a null `char` pointer is equal only to another null
pointer (or `nullptr`), not to an empty string. The other pointers and
arrays (including `uint8_t` buffers) are compared by address.

The `approx()` comparator succeeds if its first two operands differ by
less than the third one, the tolerance. The operands are numbers,
integral or floating-point, possibly of different types. For
the integers, the distance is computed exactly, also for operands of
different signedness, without wrap-around; for the other types, in
their common floating-point type. A failure is reported as
`lhs ~ (rhs +/- epsilon)`:

```cpp
t.expect (mt::approx (read_adc (), 512, 3)) << "ADC reading";
// When it fails: 509 ~ (512 +/- 3)
```

Refer to the [Function Comparators](/docs/api/groups/micro-os-plus-micro-test-plus-function-comparators/) reference page.

### Logical functions

Complex expressions may be evaluated in a single statement using the logical
functions `all_of()`, `any_of()`, and `negate()`, the function forms of the
`&&`, `||`, and `!` operators; `any_of()` is an inclusive or, true also
when all the operands are true.

```cpp
template <class First_T, class Second_T, class... Rest_T>
auto all_of (const First_T& first, const Second_T& second, const Rest_T&... rest);

template <class First_T, class Second_T, class... Rest_T>
auto any_of (const First_T& first, const Second_T& second, const Rest_T&... rest);

template <class Expr_T>
auto negate (const Expr_T& expr);
```

`all_of()` and `any_of()` take two or more operands. A chain of the same
operation is reported as a single group, for example
`(1 == 1 and abc == abd and 3 < 2)`.

All the operands are evaluated before the check, so, unlike the standard
algorithms of the same names, the functions do not stop at the first operand
that decides the result. After a `using namespace std`, an unqualified call
with three or more operands of the same type selects `std::all_of()` or
`std::any_of()`; call them as `mt::all_of()` and `mt::any_of()`.

Refer to the [Logical Functions](/docs/api/groups/micro-os-plus-micro-test-plus-logical-functions/) reference page.

### Strings

Strings are compared with `eq()` and `ne()`, which compare them by
content, and show them when the check fails (the standard `==` and `!=`
operators return a plain `bool`, so a failed check could not show the
strings):

```cpp
t.expect (mt::eq (actual, "fortytwo"sv))
    << "actual eq 'fortytwo'";
```

### Containers

Containers are compared with `eq()` and `ne()`, which use the standard
operators, and show their elements when the check fails. The containers
must be of the same type, as for the standard operators:

```cpp
t.expect (mt::eq (std::vector<int>{ 1, 2 }, std::vector<int>{ 1, 2 }))
    << "vector{ 1, 2 } eq vector{ 1, 2 }";
```

The elements are shown as `{1, 2}`, for any type that a range-based
`for` statement can iterate, with `begin()` and `end()` members, like
the standard containers, the spans, and the views, or functions, found
by argument-dependent lookup. The exceptions are the arrays, which are
compared and shown by address, as the pointers they decay to; the
strings, which are shown as text; and the types whose elements are of
their own type, like `std::filesystem::path`, which cannot be shown
element by element, and are rejected by the comparators; compare
`p.string ()` instead, or, for an application type, define an
`operator<<` for it, as for the [custom types](#custom-types). The
elements must themselves be printable.

### Other standard types

The function comparators also accept the scoped enumerations
(including `std::byte`), and the `std::pair`, `std::tuple`, and
`std::optional` objects, so also the maps, whose elements are pairs.
When a check fails, they are shown as follows:

- a scoped enumeration by its underlying value, with the suffix of its
  type, for example `1` for `int` and `1uc` for `std::byte`, whose
  underlying type is `unsigned char`; to show the names of the
  enumerators instead, define an `operator<<` for the enumeration, as
  for the [custom types](#custom-types);
- a pair or a tuple as `(a, b)`, and a map as `{(1, 2), (3, 4)}`;
- an optional by its value, or as `nullopt` when it has no value.

```cpp
enum class colour { red, green };

t.expect (mt::eq (paint (), colour::red)) << "colour is red";
t.expect (mt::ne (find (42), std::nullopt)) << "42 is found";
```

### Deprecated operators, literals, and wrappers

The overloaded operators of the `operators` namespace, the literals of the
`literals` namespace, the `to_*` type wrappers, `to_t<T>`, and the
`approx (value, epsilon)` wrapper are deprecated since 5.1.0, and will be
removed in a future release. They are still available, but the compiler
reports their use.

The function comparators provide the same checks and the same reports, with
plain values, so that the constants do not need a literal suffix and the
expressions do not need to be cast:

| Deprecated | Use |
| --- | --- |
| `x == 42_i`, `mt::to_i{ x } == 42` | `mt::eq (x, 42)` |
| `x != 42_i` | `mt::ne (x, 42)` |
| `x < 42_i`, `x <= 42_i` | `mt::lt (x, 42)`, `mt::le (x, 42)` |
| `x > 42_i`, `x >= 42_i` | `mt::gt (x, 42)`, `mt::ge (x, 42)` |
| `x == 1.5_d`, `mt::to_d{ 1.5 } == x` | `mt::approx (x, 1.5, 0.1)`, or `mt::eq (x, 1.5)` for an exact comparison |
| `mt::eq (x, mt::approx (1.5, 0.01))` | `mt::approx (x, 1.5, 0.01)` |
| `a and b`, `a or b`, `not a` | `mt::all_of (a, b)`, `mt::any_of (a, b)`, `mt::negate (a)` |
| `"flag"_b == flag` | `t.expect (flag) << "flag"` |
| `mt::to_t<app_type>{ x } == y` | `mt::eq (x, y)`, with an `operator<<` for the type |

:::warning
The overloaded `and` and `or` operators evaluate both operands before the
check, so they do not short-circuit like the built-in ones;
`p != nullptr and p->x == 1_i` dereferences a null pointer.
:::

The floating-point literals and wrappers compare with a tolerance of one
unit of the last decimal written (0.1 for `1.5_d`), derived from the digits
of the value. This is not always what the digits suggest: the tolerance of a
whole value is 0.1, and the comparison depends on which operand is wrapped.
With `mt::approx (lhs, rhs, epsilon)` the tolerance is explicit, and the
same for both operands.

Refer to the
[Operators](/docs/api/groups/micro-os-plus-micro-test-plus-operators/) and
[Literals and Wrappers](/docs/api/groups/micro-os-plus-micro-test-plus-literals/)
reference pages.

### Custom Types

The function comparators also accept **user-defined types**, provided
that the type has the operator used by the comparator: `operator==` for
`eq()` and `ne()` (in C++20, `operator==` also provides `!=`), and
`operator<=>` (or the individual relational operators) for `lt()`,
`le()`, `gt()`, and `ge()`.

Since the comparators **report the values** of their operands when a
check fails, they also need to know how to print the type. For this, the
application must define an `operator<<` that writes the value to an
`mt::expression_formatter`, in the namespace of the type, so that it is
found by argument-dependent lookup. Without it, the comparators do not
compile for that type: the call is rejected, and the diagnostic names
the type that does not satisfy `extension::printable`; only the scoped
enumerations are shown without it, by their underlying value.

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

namespace app
{
  struct point
  {
    int x;
    int y;
  };

  constexpr bool
  operator== (const point& lhs, const point& rhs)
  {
    return lhs.x == rhs.x && lhs.y == rhs.y;
  }

  // Used to report the values of failed checks.
  inline mt::expression_formatter&
  operator<< (mt::expression_formatter& formatter, const point& p)
  {
    return formatter << "{ " << p.x << ", " << p.y << " }";
  }
} // namespace app

int
main (int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise (argc, argv);

  ts.test ("Points", [] (auto& t) {
    app::point p{ 1, 2 };
    t.expect (mt::eq (p, app::point{ 1, 3 })) << "point is { 1, 3 }";
  });

  return tr.run ();
}
```

The failed check reports both values:

```console
        not ok 1 - point is { 1, 3 }
          ---
          condition: "{ 1, 2 } == { 1, 3 }"
          at:
            fileName: main.cpp
            lineNumber: 35
          ...
```

The formatter accepts the standard arithmetic types, characters,
strings, pointers, containers, scoped enumerations, pairs, tuples, and
optionals, so the members can usually be written
directly, as above. The `char` pointers and arrays, also when not
`const`, are written as strings (a null pointer as `nullptr`); the other
pointers, including the `signed char` and `unsigned char` (`uint8_t`)
pointers, are written as addresses. A plain boolean check, such as
`t.expect (p == q)`, needs no formatter, but on failure it reports only
the source location. The same `operator<<` also writes the values
appended to the messages (`t.expect (p == q) << "p is " << p`).

### Custom Comparators

When the relation to check is not one of the built-in comparisons, a
function that returns `bool` can be used, but on failure it reports only
the source location. To report the operands, as the built-in comparators
do, the function must return a framework expression, built with the
public templates of the `mt::extension` namespace:

- `extension::compare_op{ lhs, rhs, tag }`, for a comparison of two
  operands;
- `extension::predicate_op{ operand, tag }`, for a property of one
  operand.

The **tag** is an empty structure that defines the operation, with a
static `apply()` member function template, which receives the operands
and returns the result, and a static `symbol`, written in the failure
reports between the two operands, or before the single one:

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

namespace app
{
  struct divides_tag
  {
    static constexpr const char* symbol = " divides ";

    template <class Lhs_T, class Rhs_T>
    static constexpr bool
    apply (const Lhs_T& lhs, const Rhs_T& rhs)
    {
      return rhs % lhs == 0;
    }
  };

  struct even_tag
  {
    static constexpr const char* symbol = "even ";

    template <class T>
    static constexpr bool
    apply (const T& t)
    {
      return t % 2 == 0;
    }
  };

  // A custom comparator.
  template <class Lhs_T, class Rhs_T>
  constexpr auto
  divides (const Lhs_T& lhs, const Rhs_T& rhs)
  {
    return mt::extension::compare_op{ lhs, rhs, divides_tag{} };
  }

  // A custom predicate.
  template <class T>
  constexpr auto
  even (const T& t)
  {
    return mt::extension::predicate_op{ t, even_tag{} };
  }

} // namespace app

int
main (int argc, char* argv[])
{
  mt::runner tr;
  auto& ts = tr.initialise (argc, argv);

  ts.test ("Custom", [] (auto& t) {
    t.expect (app::divides (5, 12));
    t.expect (app::even (7));
    t.expect (mt::all_of (app::divides (3, 12), app::even (7)));
  });

  return tr.run ();
}
```

The failed checks report the operands, with the symbols of the tags:

```console
        ✗ FAILED (main.cpp:58, 5 divides 12)
        ✗ FAILED (main.cpp:59, even 7)
        ✗ FAILED (main.cpp:60, (3 divides 12 and even 7))
```

The expressions can be combined with the logical comparators, and,
being `constexpr`, also checked at compile time
(`static_assert (app::divides (3, 12))`). The operands are written with
the `operator<<` of the formatter, so the types of the application need
one, as for the [custom types](#custom-types).

The expressions do not copy their operands: a temporary is moved into
the expression, and a named operand of class type is referred to. The
functions above receive their operands as `const&` parameters, which
are named, so their expressions refer to the arguments of the call;
this is safe when the expression is checked in the same statement, as
in `t.expect (app::divides (5, x))`, but an expression kept in a
variable, from a call with a temporary argument, would refer to a
destroyed object. To also store such expressions, take the operands as
forwarding references (`Lhs_T&& lhs`) and pass them on with
`std::forward<Lhs_T> (lhs)`, as `eq()` does.

A helper that passes its argument on to `expect()` or `require()` can be
constrained with `extension::checkable`, as these functions are, and one
that passes it on to the message operator with `extension::printable`.

### Test suites

Test suites are named sequences of test cases.

#### Static test suites

In the common use case, test suites are static instances of the `static_suite`
class, which automatically register themselves with a static instance of the
`runner`.

The main program looks like this:

```cpp
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

mt::runner sr;

int
main (int argc, char* argv[])
{
  auto& ts = sr.initialise (argc, argv, "Top suite");

  // ... possible top suite tests ...

  return sr.run ();
}
```

Each test suite resides in a separate source file, for example:

```cpp
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

extern mt::runner sr;

static void
suite_function (mt::suite& ts)
{
  ts.test ("Check various conditions", [] (auto& t)
    {
      t.test ("Check truth", [] (auto& t) {
        t.expect (true);
      });
    });
}

static mt::static_suite suite = { "Static suite", sr, suite_function };
```

The implementation uses the C++ static constructors that are performed before the `main()` function is called. The order of registration is not defined; to provide a certain degree of predictability, the framework runs all suites when the `run()` member function is called, after **ordering them by name**.

The names are compared byte by byte, as with `strcmp()`: the comparison is case-sensitive (`"Zeta"` runs before `"alpha"`), and numbers are not compared by value (`"Suite 10"` runs before `"Suite 2"`). To run the suites in a given order, start their names with zero-padded numbers (`"01 - Init"`, `"02 - Run"`), and use the same case.

#### Non-static test suites

Static test suites are just a convenience, since they automatically register themselves with the runner, and not including the source file with the test suite in the build automatically disables the tests.

However they are not mandatory, test suites can be manually added to the
runner.

```cpp showLineNumbers
#include "micro-os-plus/micro-test-plus.h"

namespace mt = micro_os_plus::micro_test_plus;

extern void
suite_function (mt::suite& ts);

int
main(int argc, char* argv[])
{
  mt::runner tr;

  auto& ts = tr.initialise(argc, argv, "Minimal");

  ts.test ("Check truth", [] (auto& t) {
    t.expect (true);
  });

  tr.add_suite("External suite", suite_function);

  return tr.run ();
}
```

The added suites do not run in the order of the calls to `add_suite()`;
they run when `run()` is called, together with the static suites, in
the same order, by name (see above); for equal names, they run after
the static suites constructed before `main()`, in the order of the
calls.

The suites must be added before `run()` is called. A suite added while
`run()` runs, for example from the body of another suite, or after it
returned, would never run; it is rejected, the error is reported on
`stderr`, and the result is not 0.

The suite name can be a string literal, a `const char*`, a
`std::string`, or a `std::string_view`; it is copied, so the string
need not outlive the call to `add_suite()`.

#### Example

An even more elaborate example from a real-world project is:

```cpp
namespace os = micro_os_plus;
namespace mt = micro_os_plus::micro_test_plus;

// Define a function template to run the tests.
template <class T>
void
check_double_list_links (mt::suite& ts)
{
  static T left_links;
  static T links;
  static T right_links;

  ts.test ("Initial", [&] (auto& t) {
    if constexpr (T::is_statically_allocated::value)
      {
        // Check if the node is cleared.
        t.expect (mt::eq (links.previous (), nullptr)) << "prev is null";
        t.expect (mt::eq (links.next (), nullptr)) << "next is null";
        t.expect (links.uninitialized ()) << "uninitialised";

        left_links.initialize ();
        links.initialize ();
        right_links.initialize ();
      }

    t.expect (!left_links.linked ()) << "left unlinked";
    t.expect (!links.linked ()) << "unlinked";
    t.expect (!right_links.linked ()) << "right unlinked";
  });

  ts.test ("Link", [&] (auto& t) {
    // Link left as previous.
    links.link_previous (&left_links);

    // Link right as next.
    links.link_next (&right_links);

    // The node must now appear as linked.
    t.expect (links.linked ()) << "linked";

    t.expect (mt::eq (left_links.next (), &links)) << "left linked";
    t.expect (mt::eq (right_links.previous (), &links)) << "right linked";
  });

  ts.test ("Unlink", [&] (auto& t) {
    // Unlink the central node.
    links.unlink ();
    t.expect (!links.linked ()) << "unlinked";

    // Left and right must indeed point to each other.
    t.expect (mt::eq (left_links.next (), &right_links)) << "left -> right";
    t.expect (mt::eq (right_links.previous (), &left_links)) << "right <- left";
  });

  if constexpr (!T::is_statically_allocated::value)
    {
      ts.test ("Allocated on stack", [] (auto& t) {
        T stack_links;
        t.expect (!stack_links.linked ()) << "unlinked";
      });
    }
}

// Instantiate the test for statically allocated lists.
static mt::static_suite ts_static_double_list_links
    = {
        "Static double list links", sr,
        check_double_list_links<os::utils::static_double_list_links>
      };

// Instantiate the same test for regular lists.
static mt::static_suite ts_double_list_links
    = { "Double list links", sr,
        check_double_list_links<os::utils::double_list_links> };
```

Refer to the [Test Suites](/docs/api/groups/micro-os-plus-micro-test-plus-test-suites/) reference page.

### Memory Footprint

The memory footprint of unit tests based on µTest++ is generally smaller than that of traditional C++ testing frameworks, primarily because the `iostream` library is not utilised.

For example, for Cortex-M7F, the minimal test, which includes the complete functionality, requires less than 110 KB:

```
   text    data     bss     dec     hex filename
 105552    2280    3184  111016   1b1a8 minimal-test.elf
```

<details>
<summary>A similar test using [Boost UT](https://boost-ext.github.io/ut/) produced a binary over 400 KB in size.</summary>

The equivalent minimal test was:

```cpp
#include <boost/ut.hpp>

int
main(int argc, char* argv[])
{
  using namespace boost::ut;

  "Check truth"_test = [] {
    expect(true);
  };

  return 0;
}
```

```text
   text    data     bss     dec     hex filename
 410200    4452   10556  425208   67cf8 ut-minimal-test.elf
```

</details>

However, the use of templates for implementing comparators
should be used with care on platforms with severely limited memory
resources, as each unique pair of operand types contributes to the overall
programme size.

If necessary, µTest++ can be used without custom comparators,
relying solely on standard boolean expressions, while still providing the
essential functionality for testing conditions. In this configuration, the
actual values compared are not displayed on failure.

:::info
The memory footprint in `debug` builds (compiled with `-O0`) is significantly larger than in `release` builds. If required, the optimisation level for the `debug` build may be increased to `-Og` to conserve memory.
:::

#### Stack usage

The test cases run on the stack of the caller: each call to `test()`
creates the test case as a local object, and runs its body immediately,
before returning. A nested test case therefore adds its call chain to the
stack of the outer one, and the stack needed by a test grows with its
nesting depth.

The stack needed is approximately the sum of:

- a fixed part, for the runner, the suite, and the start of the first
  test case;
- a part for each nesting level, which includes the frame of the test
  case body;
- the temporary space used by the reporter at the innermost level, to
  write the results, plus that of the C library formatting functions.

For example, with GCC 15.2, the values measured with the deeply nested
test of the `suite` sample were:

| | Cortex-M33 `debug` (`-O0`) | Cortex-M33 `release` (`-Os`) | AArch64 `debug` (`-O0`) | AArch64 `release` (`-Os`) |
| --- | --- | --- | --- | --- |
| Fixed part | about 1.1 KB | about 0.7 KB | about 1.3 KB | about 1.3 KB |
| Each nesting level | 392 bytes | 200 bytes | 512 bytes | 400 bytes |

On Cortex-M33, the reporter uses about 0.5 KB more at the innermost
level, in both builds, plus the space used by `vsnprintf()`, which
depends on the C library.

Of each nesting level, 88 bytes (`debug`) and 64 bytes (`release`), on
Cortex-M33, are the frame of the test case body, which depends on the
application code: its local variables, and the calls it makes, add to
these values. The arguments passed to `test()` after the body are copied
into the frame of the test case.

The values depend on the architecture, the compiler, and the optimisation
level, so they are only an indication.

On platforms with small stacks, such as the 8 KB of the Cortex-M test
platforms, deep nesting must be planned: the deeply nested test of the
`suite` sample, with eleven levels of test cases, uses about 5 KB of the
stack in a Cortex-M33 `debug` build, before the reporter writes the
results of the innermost level. If the stack is not large enough,
increase it, reduce the nesting depth, or build the tests with `-Og`,
which, on Cortex-M33, needs about 280 bytes for each nesting level.

:::caution
Most Cortex-M cores do not detect a stack overflow: the stack grows
silently into the memory below it, usually the heap, and the test fails
later, in an unrelated place, or not at all. The ARMv8-M Mainline cores
(for example Cortex-M33) can check the stack limit, and stop with a fault
when the startup code sets the limit, as on the Cortex-M33 test platform;
a test that passes there fits in its stack.
:::

### Timings

On native platforms that support a standard way of accessing the system clock (such as the POSIX `clock_gettime()`), the µTest++ runner measures the time spent in each test suite and reports it in milliseconds alongside the results.

For example:

```
ok 1 - Minimal # { test suite passed, 1 check in 1 test case, time: 0.007 ms }
1..1
# { total: 1 check passed, 0 failed, in 1 test case, 1 test suite, time: 0.030 ms }
```

On embedded platforms using Arm semihosting, the clock resolution is in the range of tens of milliseconds — too coarse for meaningful reporting — and timings are therefore omitted from the output.

### Console output

The reporters write all console output through the standard `stdout`
stream, using `vfprintf()`, `fputs()`, and `fflush()`. Output written
by the tests with `printf()` shares the same stream and buffer, so the
two appear in the expected order.

On embedded platforms, where the output is usually forwarded to the host
via semihosting, a serial port, or a debug channel, the platform must
route `stdout` and `printf()`/`puts()`/`putchar()` to the same
destination. Platforms that redirect only `printf()` (for example via
`-Wl,--wrap=printf`) to a separate channel may interleave the test and
reporter output out of order.

µTest++ has no output hook of its own: the output is redirected by the
C library, not by the framework. On the µOS++ platforms, which provide
the C library back end, `stdout`, `stderr`, and the file operations
(`fopen()`) are forwarded to the host through Arm semihosting, so the
console output, the error messages, and the
[output file](#output-file) all reach the host without any further
configuration. In other environments, to send the output to a serial
port, RTT, or another debug channel, retarget the C library (for
example, with newlib, implement `_write()`); `stdout` and `stderr` are
then forwarded together with the `printf()` family.

The configuration errors (a missing option argument, an unknown
reporter, an output file that cannot be opened, a suite added too
late) are written to `stderr`, not through the reporter, so the
platform should forward `stderr` as well; these errors are not
written to the output file.

Semihosting requires a debugger or an emulator (such as QEMU) connected
to the target; without one, the first semihosting call faults, and the
program stops before reporting anything. Tests that run on a board
without a debugger must therefore retarget the C library to another
channel.

## C API

Whilst µTest++ can be used to test C code, its implementation relies
extensively on modern C++ features that cannot be replicated in C.

Consequently, there are no C equivalents for the C++ definitions provided
by µTest++.

## Command line options

### Verbosity

By default, µTest++ displays only **test case summaries for passing tests** (for failed tests, all expectations are shown).

To adjust the verbosity, one of the following command-line options may be specified:

- `--verbose` – display **all expectations**, irrespective of their outcome
- `--quiet` – display only the **failed checks**, with the names of the suite and of the test cases that contain them, and the **runner totals**; the TAP reporter also displays one `ok`/`not ok` line per test suite, with the plan counting them, so that the output remains a valid TAP document, which node-tap and the other TAP consumers read as failed when a suite failed
- `--silent` – suppress all output and return **solely the exit code**

The verbosity selects only the console output; the output file always receives the complete report (see [Output file](#output-file)). The table summarises what each level displays on the console:

| Level | Option | Console |
| --- | --- | --- |
| verbose | `--verbose` | all the checks, passed and failed |
| normal | (none) | a summary of each passed test case; all the checks of the failed test cases |
| quiet | `--quiet` | the failed checks, with the names of the suite and of the test cases that contain them, and the totals; with TAP, also one `ok`/`not ok` line per test suite, and the failed checks as comments |
| silent | `--silent` | nothing; only the exit code |

With the TAP reporter and the normal verbosity, the passed test cases are displayed as single `ok` lines, and the failed ones as complete `# Subtest:` blocks; the nested passed test cases appear inside the block of their outer test case. With the human reporter, the line of a passed nested test case is preceded by the name of its outer test case.

When the test execution is aborted, the totals are replaced by a line with the location of the abort, also with `--quiet`, and there is no exit code, since `run()` does not return; see [Aborting the test execution](#aborting-the-test-execution).

With `--quiet`, the failed checks are the only details displayed, so it is the level to use for a long run, in which only the failures matter. To also keep the details of the passed checks, add an output file, which receives every check, whatever the verbosity:

```sh
sample-test --quiet --output-file=sample-test.tap
```

When exceptions are not enabled and a failed requirement aborts the test
execution, the results of the aborted test case are displayed also with
`--quiet`, since the totals are never reached; see
[Aborting the test execution](#aborting-the-test-execution).

Refer to the [Command Line Options](/docs/api/groups/micro-os-plus-micro-test-plus-cli/) reference page.

### Filter

To run only some of the test suites and test cases, select them by name with the `--filter` option, as with `--grep` in node-tap. The option may be repeated, one pattern per nesting level: the first pattern applies to the suite names, the second to the test case names, and each further one to the nested test cases.

```sh
sample-test --filter='Args*|*namespace*'
sample-test --filter='*' --filter='Check one'
```

In a pattern, `*` matches any sequence of characters, `?` matches any single character, and `|` separates alternatives; the match is case-sensitive, and the pattern must cover the whole name. The suites and test cases that do not match are not run, and are reported as skipped (`ok 2 - Args suite # SKIP filtered` in TAP); the totals lines show how many were skipped.

The top suite is never skipped as a whole, since its body is `main()`, but its test cases are filtered like those of any other suite.

### List test cases

To list the test cases without running them, use the `--list-tests` option, or its short form `--list`, as in Catch2 and Boost UT. The test cases are listed under the names of their suites, followed by their number:

```console
$ sample-test --list-tests
All available test cases:
  Sample
    Check various conditions
    Check strings
  Explicit namespace suite
    Check one
    Check two
4 test cases in 2 test suites
```

With `--filter`, the header is `Matching test cases:`, and only the selected test cases are listed; the suites without selected test cases are not listed, so the two options together show what a run with the same filter would run.

The suite bodies run, as usual, since they create the test cases, but the bodies of the test cases do not run, so no check is evaluated; for the same reason, the nested test cases, created by the bodies of their parents, are not listed. No report is written: the list is written to the console, unless `--silent` is given, and to the output file, if any, and the exit code is 0 (or 2 after an option error).

The code of `main()` and of the suite bodies also runs while listing, so the parts that depend on the results of the test cases (their totals, or the exit code of `run()`), and the messages of the test program, which would be mixed with the list, should be skipped when `tr.is_listing ()` is true:

```cpp
if (!tr.is_listing ())
  {
    printf ("Starting the tests...\n");
  }
```

### Output file

To also write the report to a file, use the `--output-file` option, either as `--output-file=<path>` or as `--output-file <path>`.

The two outputs have different purposes: the console is intended for the people who watch the tests run, and its content is selected with the verbosity options, while the output file is intended for the integration with other tools (for example a CI pipeline, or a TAP consumer such as node-tap).

The output file always receives the **complete report**, whatever the console verbosity, with both reporters; the verbosity selects only what is displayed on the console. The TAP reporter is the one to use for integration, since its file is a valid TAP document, which the TAP consumers read. The file of the human reporter is intended for people, to keep the details of a run whose console output is short (see [Verbosity](#verbosity)).

### The _human_ reporter

Starting with v4.x, the default reporter is **TAP**. For compatibility with
previous versions, the original **human** reporter was preserved and can be
enabled with:

```
--reporter human
```

The output is slightly more compact, for example:

```
µTest++ human report

• Minimal

    ✓ Check various conditions - passed (2 checks)

✓ Minimal - passed (2 checks in 1 test case), time: 0.025 ms

✓ Total: 2 checks passed, 0 failed, in 1 test case, 1 test suite, time: 0.082 ms
```

The human reporter is intended for reading the console output. For the integration with other tools, use the TAP reporter, whose output file is always complete (see [Output file](#output-file)).

### Colours

The human reporter highlights the results in colour (green for the passed checks and red for the failed ones). By default, the colours are used only when the standard output is a terminal, which can be detected only on POSIX platforms (Linux, macOS); when the output is redirected to a file or a pipe, and on the other platforms, such as the embedded ones, the output is plain.

To select the colours explicitly, use the `--color` option, as in the GNU tools (`ls`, `grep`, `diff`):

- `--color=auto` – use colours only when the output is a terminal (the default)
- `--color=always`, or `--color` alone – always use colours, for example in a CI system that renders the ANSI escape sequences but does not provide a terminal, or on an embedded target whose output is displayed by a terminal
- `--color=never` – never use colours

```sh
sample-test --reporter=human --color
```

As in the GNU tools, the value must be attached with `=`; the argument that follows `--color` is never taken as its value. The GNU synonyms are also accepted: `yes` and `force` for `always`, `no` and `none` for `never`, and `tty` and `if-tty` for `auto`.

For compatibility with Catch2 and Boost UT, the alternative `--use-colour` option is also accepted, either as `--use-colour=<mode>` or as `--use-colour <mode>`, with the modes `yes`, `no`, and `auto` (and the other values of `--color`). When both options are given, the last one takes effect.

The TAP reporter never uses colours, since the escape sequences are not part of the TAP syntax, and the output file never receives them, whatever the mode. An unknown mode is reported on `stderr`, the option is ignored, and the program returns 2.
